## 2. Выжимка: что мануалы считают главным

1. **Пять подсистем харнеса**: инструкции, инструменты, среда, состояние, обратная связь (верификация). Пропущенная подсистема даёт целый класс провалов, а не «немного хуже». Порядок внедрения: обратная связь → инструкции → состояние → среда → инструменты.
2. **Инструкции — роутер, а не энциклопедия.** Входной файл 50–150 строк; детали — в тематических файлах со ссылкой «читать, когда …». Важное — в начало или конец. У правила есть источник, условие применимости и условие удаления.
3. **Правило вместо теста — антипаттерн.** Всё, что можно проверить машинно, превращается в проверку (тест, линтер, grep-гвард, hook) с сообщением WHAT / WHY / FIX, после чего текст правила из инструкций удаляется. «Должно случаться всегда — делай hook».
4. **Состояние на диске.** Агент — «инженер с амнезией»: прогресс, решения (включая отвергнутые варианты с причиной) и следующий шаг хранятся в файлах. При ~60% контекста — прекращать кодить и готовить передачу. В передаче самый ценный раздел — «Не делать».
5. **WIP = 1 и узкий скоуп.** Одна задача = одна сессия = один коммит = один e2e-сценарий. Импульс «заодно поправлю» уходит в бэклог. Нет рефакторинга до подтверждения основной функциональности.
6. **Контракт задачи до кода (sprint contract)**: в скоупе / стандарты приёмки / вне скоупа / открытые вопросы. Раздел «вне скоупа» снимает половину конфликтов «сделал не то».
7. **Готовность ставит скрипт, а не агент.** Двухуровневая проверка: глобальная (вся приёмка) + специфичная для задачи. Слабая проверка («компилируется», «выглядит правильно») — главный источник ложных «готово».
8. **Разделение генератора и оценщика.** Оценщик — отдельный чистый контекст, по возможности другая модель, вердикт по рубрике со ссылками на доказательства (файл:строка, вывод теста).
9. **Диагностика провала по слоям** (постановка → инструкции → состояние → среда → верификация → цикл), журнал провалов, ремонт от дешёвого к дорогому: сузить задачу → добавить постусловие → починить состояние → переписать инструкции → автоматизировать.
10. **Экономия контекста** (курс): `/clear` между задачами, исследование — в субагентов, короткий CLAUDE.md, детали — в skills/rules, грузящиеся по требованию; Plan mode для всего сложнее одного файла; формула промпта «цель + где искать + ограничения + как проверить».
11. **Харнес гниёт.** Регулярная ревизия: удалять устаревшее, разводить противоречия; компонент, без которого результат не хуже, удалять.

## 4. Найденные проблемы (проверены по файлам)

### 4.1. Состояние: дорогой вход в каждую задачу
- `.ai/memory/tasks.md` — 41 КБ, из них раздел «Сделано» — 20 КБ (замер `awk '/^## Сделано/{f=1} f' | wc -c`). Протокол требует читать `tasks.md` целиком на старте каждой задачи, т. е. половина чтения — архив, не нужный для работы. Оценка (не замер): порядка 5 тыс. токенов на каждый старт только на «Сделано».
- Отдельные строки бэклога до ~2000 символов: в одну запись смешаны постановка, история, ссылки на аудит и QA.
- `.ai/memory/decisions.md` — 45 КБ; правило «читать по заголовкам» есть, но агенты `react-engineer` и `react-reviewer` в своих инструкциях читают `decisions.md` без этой оговорки.

### 4.2. Инструкции: противоречия и устаревшие пути в агентах (вне репозитория)
- `~/.claude/agents/react-engineer.md:30-33` — ссылается на `.ai/memory/frontend/` и `contracts.md`, которых нет с SH-D04/SH-D11.
- `~/.claude/agents/react-engineer.md` (раздел «Правила») — «иначе выбери разумное значение по умолчанию и назови его» прямо противоречит `.ai/rules/ask-user.md` п. 1.
- `~/.claude/agents/react-engineer.md` — «после реализации спроси, добавить ли решение в файл решений» противоречит `.ai/rules/tech-approval.md` п. 2 (запись сразу после выбора, без повторного вопроса).
- `~/.claude/agents/task-planner.md:14,46` и `~/.claude/agents/solution-architect.md:45` — путь `.ai/memory/frontend/…`.
- `~/.claude/skills/project-memory/SKILL.md` — описывает раскладку `frontend/`/`backend/` + `contracts.md`.
- Это «лгущая документация» из антипаттернов Harness_ru: агент тратит шаги на поиск несуществующих файлов или действует по устаревшему правилу. Кроме того, агенты лежат вне git проекта — их изменения не ревьюятся и не воспроизводятся.

### 4.3. Верификация: дыра в статическом слое
- `npx eslint src` → 9 ошибок (`testing-library/no-node-access`, `no-container`, `render-result-naming-convention` в `Login.test.js`, `useTheme.test.js`, `Avatar.test.js`, `IconButton.test.js`). `npm run accept` линтер не запускает, CRA проверяет eslint только в `start`/`build`. Слой 1 трёхслойной валидации (статика) фактически отсутствует.
- Архитектурные правила `.ai/rules/patterns.md` (🔴 `fetch` вне `services/`, импорт `modules/*` из `services/`/`reducers/`) и `code-style.md` (без `console.log`) существуют только как текст — проверяет их только ревьюер «глазами». По модулю 10 это первые кандидаты на механизацию.

### 4.4. Постановка задачи: нет контракта, критерий общий
- Почти у всех задач бэклога критерий — «`npm run accept` = 0». Это глобальная проверка; специфичной для задачи проверки (какие `[UC-…]`/какой e2e-файл должен стать зелёным) нет. По Harness_ru это «слабая верификация»: приёмка зелёная, даже если поведение задачи не реализовано, пока старые тесты проходят.
- Нет явного «вне скоупа» и «открытых вопросов» на старте задачи. Расхождение с постановкой обнаруживается только на ревью/QA — то есть через полный цикл accept → review → QA → fix → accept → review.

### 4.5. Повторная работа в цикле приёмки
- `react-reviewer` по инструкции сам запускает `npm run accept` (Jest + Playwright + чекер). Основная сессия уже запускала приёмку перед ревью; при каждом раунде ревью полный прогон повторяется. Для QA уже есть привязка отчёта к хэшу дерева (`check-state.js --tree-hash`), для приёмки — нет.
- Ревьюер читает `state.md`, `tasks.md`, `architecture.md`, `decisions.md` целиком — около 100 КБ памяти на каждый раунд, хотя для вердикта нужны контракт задачи, диф и результаты проверок.
- Нет лимита раундов: правило «после 2 неудачных исправлений — остановиться и переформулировать» (курс, модуль 04) и «две попытки подряд по одной причине — эскалация» (Harness_ru, приём 40) не записаны.
- `react-engineer` и `react-reviewer` — обе `model: sonnet`. Harness_ru рекомендует для оценщика другую модель: разные модели ошибаются по-разному.

### 4.6. Нет механических гарантий (hooks)
- Ни в `.claude/settings.json`, ни в `~/.claude/settings.json` нет hooks. Неснимаемое правило 1 (`CLAUDE.md`: память после любых изменений + `check-memory.sh`) держится на дисциплине агента. По курсу: «должно случаться всегда — hook».

### 4.7. Дрейф памяти
- `.ai/memory/state.md` («Общее»): «Сетевого слоя … нет» — при этом существуют `src/app/services/apiClient.js` и `authApi.js` (перечислены в том же файле ниже).
- «Известные проблемы» п. 3, 6, 7 в `state.md` дублируют пометки «Из аудита FE-46» в FE-26 (`tasks.md`) — два места для одного факта.
- Маршрутизатор продублирован: таблица в `CLAUDE.md` и таблица в `.ai/README.md` — два места для синхронизации.

### 4.8. Среда
- Версия Node не зафиксирована (нет `.nvmrc`, нет `engines` в `package.json`); локально — v24.15.0.

## 5. Рекомендации по приоритету

Принцип выбора: сначала дешёвое с большим эффектом на «сделал не то» и «лишние итерации», потом экономия токенов, потом остальное. Пункты, требующие нового подхода или инструмента, по `tech-approval.md` внедряются только после выбора пользователя.

### P1 — снижает расхождение с постановкой и число итераций

**P1.1. Контракт задачи до кода** — новый файл `.ai/rules/task-contract.md` и блок в записи «В работе».

`.ai/rules/task-contract.md`:
```markdown
# Контракт задачи
Читать: при старте любой задачи разработки, до написания тестов и кода.

Перед тестами основная сессия записывает в `tasks.md` («В работе», под задачей) контракт и согласует открытые вопросы с пользователем (`ask-user.md`). Код не пишется, пока «Открытые вопросы» не пусты.

Формат:
- **Цель:** одно предложение в терминах пользователя/API (наблюдаемое поведение, не код).
- **Кейсы:** `UC-…` из `docs/user-cases.md`, которые задача делает зелёными / не должна сломать.
- **Проверка задачи:** точные команды, например `npx playwright test e2e/chats.spec.js -g "UC-CHAT-02"`, `CI=true npx react-scripts test src/app/reducers/chats.test.js`. Должна падать до реализации.
- **В скоупе:** модули/файлы.
- **Вне скоупа:** что не трогать (смежные долги, рефакторинг, стили), куда записывать замеченное — «Бэклог».
- **Открытые вопросы:** пусто или список для `AskUserQuestion`.
- **Осталось / Не делать:** обновляется по ходу; при остановке по контексту — это передача смены.

Правила:
- Ревьюер и `qa-tester` получают контракт и судят по нему; изменения вне скоупа — замечание.
- Изменение контракта по ходу работы — только с согласия пользователя.
```
Дополнить `CLAUDE.md` строкой в таблицу маршрутизатора: «Старт любой задачи разработки → … , `.ai/rules/task-contract.md`».
Дополнить `.ai/rules/memory-protocol.md` («Старт»): «Задача из бэклога → в «В работе» с контрактом по `task-contract.md`».
Дополнить `scripts/check-memory.sh`: задача в «В работе» содержит строки `Цель:`, `Проверка задачи:`, `Вне скоупа:` (по аналогии с проверкой «Осталось»).

**P1.2. Специфичная проверка в каждой задаче бэклога** — правка `~/.claude/agents/task-planner.md` и существующих записей.

История и ссылки на аудиты — одной строкой в конце или в `state.md`, а не внутри постановки. Гранулярность: одна задача = одна сессия = один коммит = один e2e-сценарий.

### P2 — механизация правил (меньше раундов ревью)

**P2.1. Линтер в приёмке** — `scripts/accept.sh`, первым шагом после `check-state.sh`:
```bash
echo "==> ESLint (src, e2e, scripts)"
npx eslint src e2e scripts --max-warnings=0
```
Предварительно исправить 9 текущих ошибок в тестах (отдельная задача). Линтер уже есть в зависимостях CRA — новой технологии нет.

**P2.2. Архитектурные гварды** — новый `scripts/arch-check.sh`, вызывается из `scripts/check-state.sh` (статическая часть, fail-fast). Сообщения в формате WHAT / WHY / FIX:
```bash
#!/usr/bin/env bash
# Исполняемые правила из .ai/rules/patterns.md и code-style.md. Сообщение: что нарушено, почему, как исправить.
set -uo pipefail
cd "$(dirname "$0")/.."
fail=0
check() { # $1 — regex, $2 — каталог, $3 — исключение (regex пути), $4 — сообщение
  local hits
  hits=$(grep -rnE --include='*.js' "$1" "$2" | grep -vE "$3" || true)
  if [ -n "$hits" ]; then echo "ARCH VIOLATION:"; echo "$hits"; echo "$4"; echo; fail=1; fi
}
check '\bfetch\(' src '^src/app/services/|\.test\.js:' \
"WHY: HTTP живёт только в services/ (patterns.md, «Слои»).
FIX: перенесите вызов в src/app/services/*Api.js через apiRequest, компонент/thunk вызывает сервис."
check "from '(\.\./)+modules/" src/app/services '^$' \
"WHY: services/ не зависит от UI (направление modules → reducers → services).
FIX: передайте нужное параметром или вынесите общее в services/."
check "from '(\.\./)+modules/" src/app/reducers '^$' \
"WHY: reducers/ не импортируют UI-модули.
FIX: селекторы и thunks не должны знать о компонентах; вынесите общее в reducers/ или services/."
check 'console\.log' src '\.test\.js:' \
"WHY: console.log не остаётся в коде (code-style.md).
FIX: удалите вызов; для диагностики используйте тест."
exit $fail
```
Сейчас скрипт упадёт на `console.log` в `Chats.js` и `JoinForm.js` (известная проблема 6 в `state.md`) — либо исправить в той же задаче, либо временно исключить эти файлы со ссылкой на FE-26/FE-44 и удалить исключение при их закрытии.
После внедрения — шаг 6 из модуля 10: в `patterns.md`/`code-style.md` заменить механизированные пункты одной строкой «проверяется `scripts/arch-check.sh`».
Альтернатива уровня 2 — правила ESLint `no-restricted-imports`/`no-restricted-globals`/`no-console` в `eslintConfig`. Это новый подход к конфигурации — только после выбора пользователя.

Механизирует неснимаемое правило 1.

**P2.4. Штамп приёмки вместо повторного прогона у ревьюера**
- `scripts/accept.sh` при коде 0 пишет `.qa/accept.json`: `{ "treeHash": <node scripts/check-state.js --tree-hash>, "date": …, "unit": N, "e2e": N, "cases": "19/19" }`.

## 7. Метрики для проверки эффекта

Считать по журналу провалов и записям задач, до и после внедрения P1–P2:
- раунды ревью на задачу (REJECT/APPROVE WITH FIXES до APPROVE) — цель: ≤ 1;
- раунды QA на задачу — цель: ≤ 1;
- доля задач, где ревью/QA нашли «сделано не то/не всё» (verification gap) — цель: < 5%;
- объём, читаемый на старте задачи (`wc -c` файлов из протокола «Старт»), — цель: снижение минимум вдвое после P3.1 и P2.3.
