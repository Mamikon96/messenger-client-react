## FE-D06 — Авторизация: поля user, срок сессии, сигнал ошибки OAuth (2026-10-05) — ЗАМЕНЕНО FE-D38
- **Решение:** уточняет FE-D04/FE-D05. (1) `user` в ответе `GET /api/auth/session` — `id`, `name`, `avatarUrl`, `provider`; email не передаётся. (2) Срок сессии — только абсолютный, 7 дней; idle-таймаута и «запомнить меня» нет. (3) Ошибка OAuth после callback — редирект на `/?auth_error=<код>` (`access_denied`, `provider_error`, `invalid_state`); фронт показывает сообщение и чистит URL через `history.replaceState`. Контракт целиком — `auth-contract.md`.
- **Почему:** минимальный набор данных профиля (меньше персональных данных); абсолютный срок проще для сервера; параметр в URL работает без роутера (FE-D04).
- **Альтернативы:** `user` с email (больше персональных данных, нужен только для связывания аккаунтов); idle 30 минут + абсолютный срок 7 дней; срок не фиксировать в контракте; ошибка OAuth через одноразовую временную cookie, отдаваемую `/api/auth/session` (сложнее).
- **Замена (2026-10-13):** все три пункта устарели — `user` теперь `SessionUser` из шести полей без `provider`, сессия скользящая 400 дней, OAuth и `auth_error` удалены (FE-D38, спека `docs/auth-password-spec.md`).

## FE-D30 — WebAuthn: нативные методы браузера + свой хелпер сериализации (2026-10-13) — ЗАМЕНЕНО FE-D38
- **Решение:** опции и ответы WebAuthn переводятся между JSON сервера и браузерным API нативно (`PublicKeyCredential.parseCreationOptionsFromJSON`/`parseRequestOptionsFromJSON`, `credential.toJSON()`), где браузер их поддерживает; иначе — собственный хелпер src/app/services/webauthn.js (новый файл; base64url, `clientExtensionResults`) по образцу `docs/client-passkeys-guide.md` §4, с unit-тестами. Без новых зависимостей. Нет `window.PublicKeyCredential` — сообщение «браузер не поддерживает вход по ключу».
- **Почему:** выбор пользователя: `browserslist` production шире нативной поддержки (Chrome 129+, Firefox 119+, Safari 18.4+ по MDN на момент гайда), хелпер — около 80 строк кода без зависимости.
- **Альтернативы:** `@simplewebauthn/browser` (новая зависимость ради небольшого кода); только нативные методы (часть пользователей Safari/Firefox не войдёт); не выбраны.

## FE-D32 — e2e входа по passkey на mock-BFF без криптопроверки (2026-10-13) — ЗАМЕНЕНО FE-D38
- **Решение:** mock-BFF переводится на контракт passkey (`docs/client-integration.md` §2): отдаёт опции церемоний, принимает `credential` по форме без криптографической проверки, ведёт инвайты, сессии, «Мои ключи» и админку в памяти. e2e используют виртуальный аутентификатор Playwright через CDP (`WebAuthn.addVirtualAuthenticator`). OAuth-часть mock-BFF и `/mock-provider` удаляются. Совместимость с настоящим бэкендом проверяется вручную или проходом `qa-tester` с `messenger-server`.
- **Почему:** выбор пользователя: приёмка остаётся автономной и быстрой, не зависит от другого проекта и базы данных.
- **Альтернативы:** e2e против настоящего `messenger-server`; оба варианта (mock в приёмке + ручной набор против бэкенда); не выбраны.

## FE-D33 — Гайд бэкенда `docs/client-passkeys-guide.md` — локальная копия вне git (2026-10-13) — ЗАМЕНЕНО FE-D38
- **Решение:** как и `docs/client-integration.md` (FE-D12), гайд перехода на passkey — локальная копия документа `messenger-server`, внесён в `.gitignore`. Источник истины по контракту — спецификация `docs/client-integration.md`; при расхождении гайда и спецификации верна спецификация. Локальная копия спецификации обновляется на версию passkey (бэкенд, коммит `2f664c7`) в первой задаче миграции вместе с удалением OAuth: `scripts/check-state.js` сверяет код, mock-BFF и кейсы с копией, и замена без миграции делает приёмку красной.
- **Почему:** выбор пользователя: документ принадлежит бэкенду; версионирование копии в клиенте даёт расхождение версий.
- **Альтернативы:** коммитить гайд в репозиторий клиента; не выбрано.

## FE-D34 — e2e входа: ключ засевается в виртуальный аутентификатор через CDP `WebAuthn.addCredential` (2026-10-13) — ЗАМЕНЕНО FE-D38
- **Решение:** в e2e на mock-BFF (FE-D32) тест добавляет в виртуальный аутентификатор Playwright ключ (`WebAuthn.addCredential`, discoverable, `rpId` `localhost`) с `userHandle` заранее засеянного пользователя mock-BFF; вход идёт через обычный экран «Войти с ключом». Служебных маршрутов в mock-BFF для этого нет; подпись mock-BFF не проверяет.
- **Почему:** выбор пользователя по FE-60: детерминированно, без зависимости входа от `/invite` (FE-64) и без маршрутов вне контракта, которые `scripts/check-state.js` сочтёт расхождением.
- **Альтернативы:** регистрация через UI по приглашению из служебного маршрута mock-BFF (ближе к реальному пути, но FE-60 зависит от FE-64 и появляется неконтрактный маршрут); не выбрано.
