# FE-96 (P1)

apiClient: после `403 csrf_invalid` — перечитать `GET /api/auth/session` (single-flight: параллельные запросы ждут одно перечитывание) и повторить исходный запрос один раз; если после перечитывания сменился `user.id` (в другой вкладке вошёл другой пользователь) — сбросить store, данные прежнего пользователя не видны; повторный `403` — ошибка запроса, не выход из системы (FE-D38, спека `docs/auth-password-spec.md` §12.2). Вынесено из FE-35. Кейсы: UC-SESSION-09 (перевод в active — с разрешения пользователя); не сломать UC-SESSION-05. Проверка: unit `src/app/services/apiClient.test.js` (повтор один раз, single-flight, смена `user.id`) и e2e по кейсу (две вкладки в одном контексте) падают до реализации. Критерий: `npm run accept` = 0. Зависит от: FE-56, FE-87, FE-89. В той же задаче: mock-BFF отдаёт `403 {error:{code:"csrf_invalid"}}` вместо пустого тела (сейчас `logout` и прочие `/api/*` при неверном CSRF — пустой `403`; найдено ревью FE-88, решение пользователя 2026-10-14) + контрактный тест.
