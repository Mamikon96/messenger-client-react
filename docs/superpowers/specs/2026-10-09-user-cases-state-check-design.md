# User-кейсы и проверка состояния системы — дизайн

Дата: 2026-10-09 · Ветка: `chore/user-cases-state-check` · Статус: утверждён дизайн; реализация в процессе

## Цель
Единый документ user-кейсов — источник истины о том, что умеет продукт. Скрипт проверки состояния определяет рассинхрон между API-контрактом, кодом и поведением; мерило успеха — соответствие документу кейсов. E2E-тесты покрывают все кейсы, и это проверяется механически. Документ меняется только с разрешения пользователя.

## Решения пользователя
- Охват: `active` (реализованные) + `planned` (из бэклога FE-33…FE-45).
- Защита: контрольная сумма + скрипт утверждения, который запускает только пользователь.
- Рассинхрон: API↔код (эндпоинты), код↔кейсы (покрытие), поведение (прогон e2e), контракт mock-BFF↔API.
- В каждый кейс добавляются человекопонятные описания.

## 1. Документ `docs/user-cases.md` (в git)
Каждый кейс — блок:

```
### UC-AUTH-01 — Вход через провайдера
Статус: active
Описание: Человек открывает приложение, видит кнопки «Войти через Google/GitHub», нажимает одну — и попадает в мессенджер под своим именем. Без входа мессенджер не виден.
Шаги: 1. Открыть `/`. 2. Нажать «Войти через GitHub».
Ожидается: открывается мессенджер; в меню пользователя имя из аккаунта провайдера.
API: GET /api/auth/:provider/start
```

- `Описание` — обязательное, 1–3 предложения простым языком, без терминов кода (что видит и делает человек, зачем это ему). Для читателя без техподготовки.
- `Статус` ∈ `active|planned`; `Шаги`, `Ожидается` — обязательны; `API:` — ноль или больше строк `METHOD /path`.
- ID `UC-<ОБЛАСТЬ>-NN` уникальны. Области: AUTH, SESSION, THEME, CHAT, MSG и т. д.
- Первый черновик набора пишет агент; в силу вступает после `bash scripts/approve-usecases.sh`, запущенного пользователем.

## 2. Защита от правок без разрешения
1. `.ai/user-cases.sha256` — хэш документа; пишет только `scripts/approve-usecases.sh`.
2. `.claude/settings.json`: deny на Edit/Write для `docs/user-cases.md`, `.ai/user-cases.sha256`, `scripts/approve-usecases.sh` и на Bash-запуск `approve-usecases.sh`; пользователь запускает его сам через `! …`.
3. Правило 7 в `CLAUDE.md`: документ меняется только по явной просьбе; при необходимости изменить кейс агент спрашивает пользователя.

Оговорка: хэш защищает от «тихих» правок, не от злонамеренного переписывания хэша — поэтому слои 2 и 3.

## 3. `scripts/check-state.sh` (+ `scripts/check-state.js`, только встроенные модули Node)
Включает `check-memory.sh`, затем:
- **Хэш:** документ совпадает с утверждённым; формат кейсов валиден (поля, уникальность ID, непустое `Описание`).
- **Покрытие:** у каждого `active`-кейса есть e2e-тест с тегом `[UC-…]` в названии; тег на несуществующий кейс — ошибка; тест на `planned`-кейс — ошибка (сначала пользователь переводит в `active`); запрещены `test.skip/fixme/only`, тест без `expect`.
- **API↔код:** эндпоинты контракта `docs/client-integration.md` (заголовки разделов 2–3) сверяются с `/api/...` в `src/` и маршрутами `mock-bff/server.js`: вызов клиента вне контракта — ошибка; маршрут mock-BFF вне контракта — ошибка; `API:` у `active`-кейса без маршрута в mock-BFF — ошибка. Контракта нет (он в `.gitignore`) — предупреждение и пропуск.
- **Поведение (`--behavior`):** прогон e2e с JSON-репортёром, матрица «кейс → прошёл/упал»; упавший тест = нарушенный кейс. Успех: все `active` покрыты и зелёные.

## 4. Интеграция и ужесточение
- `scripts/accept.sh`: `check-state.sh` вместо `check-memory.sh`; e2e идёт через `check-state.sh --behavior`.
- `playwright.config.js`: `forbidOnly: true`, `retries: 0`.
- Существующие e2e получают теги `[UC-…]`; недостающие кейсы дописываются тестами вперёд.
- Обновляются `.ai/rules/testing.md`, `acceptance.md`, `CLAUDE.md`, `.ai/memory/README.md`; решение — FE-D16 в `decisions.md`.
- Тесты чекера: `node --test scripts/` на фикстурах (битый хэш, кейс без теста, тест без кейса, неизвестный эндпоинт, пустое описание).

## 5. Агент-тестировщик `qa-tester` (FE-D17)
- `.claude/agents/qa-tester.md`: сам поднимает mock-BFF и dev-сервер, проходит в браузере (Playwright MCP — основной проход, Chrome DevTools MCP — консоль и сеть) все `active`-кейсы по полям «Шаги»/«Ожидается», код не правит, пишет `.qa/report.md` (вне git) и скриншоты.
- Отчёт: шапка `Дерево:` (хэш кода: `check-state.js --tree-hash`), `Кейсы:` (sha256 документа), `Вердикт: PASS|FAIL`; матрица всех active-кейсов (`pass|fail|blocked`); проблемы `### QA-N [BLOCKER|MAJOR|MINOR|NIT] UC-… — …`.
- Цикл: основная сессия запускает агента после зелёного `npm run accept` → FAIL → `react-engineer` исправляет → accept → повторный проход. Устаревание отчёта автоматическое (хэш дерева кода и хэш кейсов).
- Гейт: правило в `acceptance.md`/`CLAUDE.md` + `check-state.sh --require-qa` (PASS, все active = pass, нет открытых BLOCKER/MAJOR, отчёт свежий), вызывается из `git-task.sh commit` для коммитов с `src/` или `mock-bff/`.
- Playwright e2e из приёмки не убирается: он детерминирован и держит покрытие кейсов; агент дополняет его там, где нужны глаза (вёрстка, UX, консоль/сеть).

## Не входит (YAGNI)
Unit-тесты как покрытие кейсов; автогенерация тестов из кейсов; CI-интеграция (репозиторий без CI).

## Порядок работ
1. Утверждение этого дизайна → черновик `docs/user-cases.md` → утверждение пользователем (`approve-usecases.sh`).
2. Тесты чекера (падают) → `check-state.js/.sh` → интеграция в `accept.sh`.
3. Теги в существующих e2e, недостающие e2e вперёд реализации, при необходимости правки кода.
4. Правила, память, `npm run accept`, ревью, коммит, PR.
