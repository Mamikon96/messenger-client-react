## SH-D05 — Решение фиксируется сразу после выбора пользователя; пишет solution-architect (2026-10-05)
- **Решение:** после ответа пользователя на `AskUserQuestion` решение с обоснованием («Решение / Почему / Альтернативы») записывается в `decisions.md`: если варианты готовил `solution-architect` — он сам (ему выдан `Edit` только для `decisions.md`, основная сессия передаёт ему выбор через `SendMessage`), иначе основная сессия. ## SH-D07 — PR создаётся автоматически после коммита задачи; ветка удаляется автоматически после слияния (2026-10-05)
- **Решение:** после `git-task.sh commit` агент сам пушит ветку и создаёт PR в `main` (пока нет `develop` в `origin`), без строки «Generated with Claude Code» в описании. Слияние и теги — по-прежнему только по просьбе. В репозитории включено «Automatically delete head branches»; `develop` и `release/*` защищены ruleset `protect-develop-release` (запрет удаления). Меняет прежнее «push и PR — только по просьбе» в `git-flow.md`.
- **Почему:** владелец проекта хочет, чтобы цикл задачи доходил до PR без лишних просьб, а ветки не копились. У GitHub нет галочки удаления при создании PR (есть только при слиянии), поэтому надёжнее настройка репозитория, чем флаг в каждой команде.
- **Альтернативы:** `gh pr merge --delete-branch` только при слиянии вручную (не работает при слиянии кнопкой в вебе); `gh pr merge --auto --delete-branch` при создании PR (требует auto-merge и противоречит правилу «слияние только по просьбе»).

## FE-D04 — Авторизация: OAuth Google/GitHub через BFF с httpOnly-cookie сессией (2026-10-05) — ЧАСТИЧНО ЗАМЕНЕНО FE-D38
- **Решение:** (1) вход только через OAuth Google/GitHub к своему API (бэкенд отдельный, пока не существует; контракт фиксируется заранее, на фронте мокается); email+пароль, passkeys, 2FA не делаем. (2) Архитектура BFF: кнопка провайдера делает полную навигацию на `/api/auth/{provider}/start`, код меняет сервер (state + PKCE), сессия хранится в cookie `HttpOnly; Secure; SameSite=Lax`, изменяющие запросы несут CSRF-заголовок. (3) Топология: SPA и API на одном сайте, только веб, других клиентов нет. (4) Фронт: слайс `auth` (`status` + `user`), единый apiClient с глобальной обработкой 401, сброс всего store при logout; в Redux и localStorage нет токенов и csrfToken; `loginService`/ключ `user` в localStorage уходят. (5) Без роутера: гейт по `auth.status` в `src/App.js`. (6) Мок M3 + M1: в Jest — подмена fetch/`authApi`, в Playwright — `page.route`, плюс локальный Node mock-BFF через CRA proxy для dev и e2e (затрагивает `playwright.config.js` и `scripts/accept.sh`).
- **Почему:** BFF — рекомендация RFC 10017 для приложений с персональными данными, и токены не попадают в JS; самый простой и тестируемый фронт, без новых пакетов; один сайт и отсутствие других клиентов снимают главный минус cookie-сессии; mock-BFF даёт настоящие редиректы, httpOnly-cookie и 401, близко к бою.
- **Альтернативы:** B — access в памяти + refresh-cookie с ротацией (отклонён: по RFC слабее BFF, сложный фронт — single-flight refresh, гонки между вкладками; нужен только для разных доменов или многих клиентов); C — только контракт + фейковый authApi (отклонён: не проверяет редиректы, cookie, 401 и CSRF, решение просто откладывается); MSW (отклонён: не эмулирует httpOnly-cookie и навигации, несовместим с Jest 27 в CRA без обходов, 3.0 слишком свежий); react-router-dom@7 (отклонён: сейчас не нужны URL и deep-links, достаточно гейта; v8 несовместим с React 18).

## FE-D05 — Авторизация: dev-прокси, контракт auth API, CSRF и истечение сессии (2026-10-05)
- **Решение:** уточняет FE-D04. (1) Dev-прокси — файл src/setupProxy.js (будет создан) на `http-proxy-middleware` 2.x, явно в devDependencies. (2) Контракт auth API ведётся Markdown-документом в `.ai/memory/` (не OpenAPI). CSRF-токен фронт получает из тела ответа `GET /api/auth/session`, хранит только в модуле apiClient (не в Redux и не в localStorage), отправляет в заголовке `X-CSRF-Token`. (3) Истечение сессии (401): сразу переход в `anonymous`, сброс store, экран входа с сообщением «сессия истекла»; черновик и открытый чат не сохраняются.
- **Почему:** поле `proxy` в package.json не проксирует навигацию (`Accept: text/html`), а `/api/auth/{provider}/start` — это полная навигация; явная зависимость не ломается при обновлении react-scripts. Markdown-контракт и токен в теле `/session` — выбор пользователя, без лишних инструментов. Простое поведение при 401 — выбор пользователя.
- **Альтернативы:** транзитивная копия `http-proxy-middleware` из react-scripts (хрупко); свой Node-прокси, объединяющий SPA и mock-BFF (сложнее); OpenAPI-файл для контракта; CSRF по схеме double-submit через читаемую cookie; модалка «войдите снова» с сохранением черновика.

## FE-D07 — UI: дизайн-токены на CSS custom properties и свой CSS, без UI-библиотек (2026-10-08)
- **Решение:** редизайн UI строится на дизайн-токенах (CSS custom properties: цвета, типографика, отступы, радиусы, тени, анимации). Темы переключаются атрибутом `data-theme` на `<html>`. ## FE-D08 — UI: три режима темы — светлая, тёмная, «как в системе» (2026-10-08)
- **Решение:** режимы `light` / `dark` / `system`. По умолчанию `system` (следует `prefers-color-scheme`), выбор пользователя хранится в localStorage (это настройка интерфейса, не данные сессии, FE-D04 не нарушается; сбрасывать при logout не нужно). Тема выставляется на `<html data-theme>` до первой отрисовки, без вспышки. Набор токенов рассчитан на добавление новых тем без правок компонентов. Развивает FE-D07.
- **Почему:** выбор пользователя; «как в системе» даёт верный первый визит, остальное — явное управление.
- **Альтернативы:** только светлая/тёмная без автоопределения; несколько акцентных цветовых схем × светлая/тёмная (больше токенов и тестов, не выбрано).

## FE-D15 — Поведение клиента по пакету 8а `docs/client-integration.md` (2026-10-09)
- **Решение:** принято целиком. (1) Отправка: очередь только в памяти; автоповтор с тем же `clientId` на сеть/5xx/429 (с `Retry-After`) с backoff, затем статус `failed` и кнопка «Повторить»; число попыток уточняется при реализации FE-40. (2) Стор нормализуется до UI-задач FE-26/FE-27: `createEntityAdapter`, сообщения по `chatId` с ключом `seq`, pending-сообщения по `clientId`, `activeChatId` вместо копии чата. (3) `csrfToken` только в памяти; при `403 csrf_invalid` один раз перечитать `GET /api/auth/session` и повторить запрос. (4) WS-реконнект: экспоненциальный backoff с full jitter и потолком; `4008` — баннер «открыто в другой вкладке» с кнопкой «Подключиться», без автоповтора; `online`/`visibilitychange` — немедленная попытка и сверка `GET /api/chats`. (5) `POST …/read` — по максимальному видимому `seq` при видимой вкладке, с debounce. (6) Кэш истории и `lastKnownSeq` — в Redux (без IndexedDB); догонка `since` только по чатам с загруженной историей. (7) Непрочитанные и чаты, созданные в другой вкладке, синхронизируются перечитыванием `GET /api/chats` при фокусе (без BroadcastChannel). (8) FE-19 закрывается: сервер сам закрывает сокеты другой вкладки кодом `4401` (≤ 30 с). (9) Единый обработчик «сессия закончилась» для REST-401, WS-`4401` и `1006` до `open` при `401` от `/api/auth/session`: закрыть сокет, сбросить store, экран входа «сессия истекла» (FE-D05(3)). (10) Элемент списка из `ChatDto` (`chat.created`, `POST /api/chats`) клиент собирает сам, `peer` — из `members`. (11) `clientId` — обёртка над `crypto.randomUUID` с запасным вариантом на `crypto.getRandomValues`. (12) Линкификация `body` отложена; пока только экранирование React.
- **Почему:** выбор пользователя; без новых зависимостей и персистентности, в рамках Redux Toolkit (FE-D01); соответствует правилам документа (раздел 5–6: идемпотентность по `clientId`, догонка через REST, реакция на коды закрытия) и малой группе (SH-D09).
- **Альтернативы:** очередь неотправленных и кэш истории в IndexedDB (персистентность между перезагрузками — сложнее, миграции); BroadcastChannel для синхронизации вкладок (лишний канал, перечитывания при фокусе достаточно); RTK Query для серверных данных (новый подход, плохо сочетается с WS-событиями и нормализацией по `seq`); linkifyjs для ссылок в `body` (новая зависимость, отложено); догонка по всем чатам (лишние запросы).

- **Решение (выбор пользователя):** кейсы проходятся в Playwright MCP, после каждого кейса — его `browser_console_messages` и `browser_network_requests`; при `fail` или ошибке консоли/сети кейс повторяется в Chrome DevTools MCP, в отчёт идут стек ошибки (`get_console_message`) и тела запросов/ответов (`get_network_request`).
- **Почему:** Chrome DevTools MCP запускает отдельный браузер — прежняя инструкция «проходить в Playwright, консоль смотреть в Chrome DevTools» смотрела в другой браузер; повтор только проблемных кейсов даёт глубокую диагностику без двойного прохода.
- **Альтернативы (не выбраны):** Chrome DevTools как основной браузер (переписывать «Стенд: известное»); оба браузера на каждый кейс (~2× токенов QA).

## FE-D45 — Поиск людей, direct-чат из поиска, пустые группы и приглашение (2026-10-17)
- **Решение (выбор пользователя):** (1) поиск людей серверный — `GET /api/users?q=&limit=` (добавляет бэкенд: `q` от 2 символов, без себя, только по `name`, `login` в выдаче нет); клиент — хук `useUserSearch` (debounce + `AbortController`, локальное состояние, не в RTK) и presentational `PeopleSearch` с действием на строке `getAction(user) → {label, icon, disabled, onClick}`. (2) Поиск — в левой панели над списком чатов; действие «Написать <имя>» → `POST /api/chats {type:"direct", userId}`, на 201/200 — upsert чата и открытие; `JoinForm` и `chatCreated` удаляются. (3) Группа создаётся без участников (бэкенд разрешает `memberIds: []` и добавляет удаление группы владельцем); «Новая группа» — кнопка в левой панели, только название. (4) «Пригласить» = сразу добавить (`POST /api/chats/:id/members`), только owner; кнопка в шапке диалога → модалка с тем же `PeopleSearch` (участники — disabled «уже в чате»); после 204 — перечитать `GET /api/chats/:id` до FE-41.
- **Почему:** фильтрация всего `/api/users` на клиенте раскрывает список всех пользователей при открытой регистрации; поиск без `login` защищает от перебора логинов; один `PeopleSearch` с действием на строке обслуживает и новый чат, и приглашение.
- **Альтернативы (не выбраны):** клиентская фильтрация `GET /api/users` (утечка списка пользователей); модалка «Новый чат» из хедера (выбран поиск в левой панели, как в Telegram); группа с обязательным ≥1 участником (бэкенд разрешит пустую); приглашения с согласием приглашённого (отложены в бэклог).

## FE-D46 — Отправка сообщений: ретраи, статусы иконками, лимит длины, local-чаты (2026-10-17)
- **Решение (выбор пользователя):** (1) автоповтор на сеть/`5xx`/`429` — 3 попытки с экспоненциальным backoff 1 с → 2 с → 4 с и джиттером (при `429` пауза из `Retry-After`), затем `failed`; уточняет число попыток из FE-D15(1). (2) Статус своего сообщения — иконка рядом с ним, как в Telegram: часы (`sending`), одна галочка (`sent`), красный треугольник с «!» внутри (`failed`) — это кнопка (курсор-указатель, ховер, видимый фокус), нажатие на неё — «Повторить» с тем же `clientId`; у иконок доступное имя («Отправляется», «Отправлено»; у кнопки — «Не отправлено. Повторить»). Иконки — inline SVG без библиотеки, цвет через токены темы. Двойная галочка «прочитано» — вне FE-40 (FE-43). (3) Текст длиннее 4000 кодовых точек: Send и Enter не отправляют, над полем счётчик «N / 4000» с `role="alert"`, текст в поле не обрезается. (4) В local-чатах (`local: true`, кнопка Join) отправка остаётся локальной без `POST` и без иконки статуса; JoinForm удаляется в FE-44.
- **Почему:** 3 попытки (~7 с) быстро показывают ошибку и не нагружают сервер; иконки компактнее текста и привычны пользователю; inline SVG не добавляет зависимость ради трёх иконок; блокировка с счётчиком не теряет текст; local-чатов нет на сервере, и `POST` в них всегда вернёт `404`.
- **Альтернативы (не выбраны):** 5 попыток (около 30 с в статусе «отправляется»); без автоповтора (противоречит FE-D15(1)); текстовые статусы; видимая кнопка «Повторить» рядом с иконкой; библиотека иконок (lucide-react); ошибка без счётчика или молчаливое обрезание текста; `POST` в local-чаты со статусом `failed`.

## FE-D47 — qa-tester: дешёвый режим прохода (2026-10-17)
- **Решение:** уточняет FE-D17, FE-D43. Агент `qa-tester` по умолчанию на модели sonnet (было opus); основная сессия может запустить его с `model: opus` для рискованной задачи. Агенту запрещено открывать скриншоты через `Read`; скриншот только при `fail`. В инструкции бюджет ходов: ~8 на кейс, ~60 на проход, при превышении оставшиеся кейсы `blocked`, вердикт FAIL.
- **Почему:** замер 12 проходов: чтение кэша 0,4–21 млн токенов на проход (FE-40: 240 ходов, 21 млн; FE-39: 137 ходов, 8 млн), на Opus. Стоимость определяет число ходов, умноженное на растущий контекст, а не размер ответов Playwright; картинки из `Read` остаются в контексте до конца прохода.
- **Альтернативы (не выбраны здесь):** убрать smoke из обычного объёма и ввести полный проход по триггерам — вынесено в FE-116 (меняет скрипты и FE-D35); оставить Opus — дороже, качество находок не измерено.


## FE-D48 — QA: кейсы про отказы и тайминги не проходятся в браузере (2026-10-17)
