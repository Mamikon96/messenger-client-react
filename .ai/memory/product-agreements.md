# Соглашения по продукту, архитектуре и бэкенду
Читать: при старте проекта бэкенда, проектировании контракта API/событий, задач про реалтайм и серверное хранение. Основание: SH-D09, SH-D10 (`decisions.md`).

## Цель и рамки (SH-D09)
- Реальный мессенджер для малой закрытой группы: до ~1 000 пользователей, один сервер.
- Безопасность: TLS на транспорте, сессия по cookie (контракт — `docs/client-integration.md`, FE-D12), без E2EE.
- Бэкенд — отдельный проект/репозиторий (`messenger-server`, реализованы фазы 1–4: auth, чаты, сообщения, WebSocket); этот репозиторий — frontend.
- Не входит (YAGNI на старте): публичный масштаб и горизонтальное масштабирование, E2EE, федерация, корпоративные SSO/аудит.

## Основа бэкенда (SH-D10)
- Node.js + WebSocket + PostgreSQL. Библиотеки — отдельное согласование по `tech-approval.md`.
- Отклонены: BaaS (Supabase/Firebase), Matrix (Synapse), «только клиент на mock-сервере».
- Не выбрано отдельно: SSE+POST как запасной транспорт, SQLite как альтернатива PostgreSQL (в SH-D10 принят PostgreSQL), конкретные библиотеки сервера.

## Из чего состоит мессенджер
| Слой | Что входит |
|---|---|
| Ядро | Чаты (1:1, группы), участники и роли, сообщения, история с пагинацией |
| Реалтайм | Доставка новых сообщений, переподключение и догонка пропущенного |
| Состояние | Статусы сообщений, непрочитанные, presence, «печатает» |
| Дополнительно | Медиа и файлы, поиск, ответы, правки и удаление, реакции |
| Платформа | Уведомления (Web Push), безопасность, лимиты, наблюдаемость |

## Проектные соглашения (рекомендации исследования; уточнять в проекте бэкенда)
- **Идемпотентность:** клиент генерирует `clientId` сообщения, сервер отвечает идемпотентно; дубли при повторной отправке не создаются.
- **Порядок:** задаёт серверный `seq` внутри чата, не `Date.now()` клиента; время — серверное.
- **Догонка:** клиент хранит последний `seq` по чату и после реконнекта запрашивает `since=seq`.
- **Статусы:** `sending` → `sent` / `failed`, повторная отправка из UI. `delivered` и `read` бэкенд пока не поддерживает (чужой `last_read_seq` не отдаётся, событий о прочтении нет — docs 8б.1, 8б.6).
- **Непрочитанные:** у участника чата `last_read_seq`; счётчик считается от него.
- **Presence и typing:** эфемерные события, в БД не пишутся, на клиенте и сервере throttle.
- **История:** курсорная пагинация по `seq`, не offset; на клиенте виртуализация длинных списков.
- **Медиа:** загрузка в объектное хранилище по presigned URL; проверка типа и размера.

## Безопасность
- WebSocket: аутентификация cookie-сессией, проверка `Origin` (защита от cross-site WebSocket hijacking), проверка членства в чате на **каждом** событии, а не только при подключении.
- CSRF для изменяющих запросов (как в контракте auth); текст сообщений рендерится только как текст, ссылки санитизируются (XSS).
- Лимиты: размер сообщения, частота отправки, размер файлов.

## Клиент (frontend)
- Нормализованный стор (`architecture/store.md`) и сервис сокета `src/app/services/wsService.js` с диспатчем событий в store (`src/app/reducers/realtime.js`) уже есть.
- Несколько вкладок: каждая открывает свой сокет — связано с FE-19.
- Доступность: новые сообщения через `aria-live`, прокрутка не прыгает при подгрузке истории.
- Тесты: e2e реалтайма идут через WebSocket-моки Playwright (FE-D13), реальный тестовый бэкенд не требуется.

## Фазы продукта
Порядок работ: 1) основа: контракт API и событий, схема БД, каркас сервера, auth; 2) чаты и участники; 3) сообщения: REST, история, нормализация стора; 4) реалтайм: WebSocket, `seq`, догонка, оптимистичный UI, статусы; 5) присутствие: непрочитанные, presence, typing; 6) правка и удаление, ответы, поиск; 7) медиа и Web Push; 8) платформа: лимиты, логирование, деплой.
Контракт зафиксирован (`docs/client-integration.md`); frontend-задачи ведутся в `tasks.md` и `done.md` (FE-32…FE-45 и далее), бэкенд-задачи — в проекте бэкенда.
