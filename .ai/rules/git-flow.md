# Git: коммиты и ветки (git-flow)
Читать: перед ЛЮБОЙ git-операцией — коммит, создание/слияние ветки, тег, push, PR.

## Общие правила
- Ветка задачи и коммит по её завершении делаются **автоматически** (раздел «Автоматический цикл»). Всё остальное — push, PR, слияние, теги, удаление веток, `--amend` — **только по явной просьбе пользователя**; разрешение на одно действие не распространяется на следующие.
- Не использовать `--force`, `reset --hard`, `--no-verify`, `commit --amend` уже опубликованных коммитов без явного «да».
- Перед коммитом: `git status` + `git diff --staged`; в коммит попадает только то, что относится к задаче. Файлы добавлять по именам, не `git add -A`.
- Не коммитить секреты, `.env`, `node_modules`, `build/`, артефакты Playwright (`test-results/`, `playwright-report/`).
- Перед коммитом память актуальна (`tasks.md`, штамп) и `bash scripts/check-memory.sh` = 0 (`memory-protocol.md`).
- Один коммит — одно логическое изменение. Тесты и реализация новой фичи — в одном PR; тесты пишутся до реализации (`testing.md`), коммит может быть один — по завершении задачи.

## Автоматический цикл (делает агент без отдельной просьбы)
Хелпер: `bash scripts/git-task.sh` (проверяет ветку, формат сообщения, запрещённые файлы и `check-memory.sh`; ничего не пушит и не сливает).

**1. Старт или продолжение задачи** — первым шагом, до правок кода. `start` сначала **проверяет состояние и только потом** переключается/создаёт ветку; при любой ошибке ветка не меняется:
- Задача из бэклога: `bash scripts/git-task.sh start FE-NN <slug>` (`bugfix` третьим аргументом — для бага). Работа вне бэклога: `start chore <slug>`.
- Проверки (в таком порядке):
  1. **Репозиторий корректен:** нет незавершённых merge/rebase/cherry-pick/revert/bisect, нет конфликтов, не detached HEAD.
  2. **Задача корректна:** `FE-NN` есть в «В работе» или «Бэклог» `tasks.md` (закрытая или незаведённая — ошибка; для `chore` не проверяется).
  3. **Чистое дерево:** если ветка меняется, а в рабочем дереве есть чужие незакоммиченные изменения — отказ (иначе они «приедут» в ветку задачи). `--allow-dirty` — только с согласия пользователя; такие файлы не включать в коммит задачи.
  4. **База актуальна:** `git fetch origin`; `develop` (если её нет — `main`) отстаёт от `origin` → подтягивается fast-forward; разошлась → ошибка; `fetch` недоступен → предупреждение.
  5. **Память актуальна:** `scripts/check-memory.sh` = 0.
- После проверок: ветка уже есть → переключение (продолжение; если отстаёт от базы — только сообщение, rebase/merge по просьбе); нет → создаётся `feature/FE-NN-<slug>` от `develop`.
- Нет `develop` → скрипт локально создаёт её от `origin/develop` или `main`.
- Ошибка проверки — не обходить, а исправить причину (обновить `tasks.md`, закоммитить/убрать чужие правки, разобрать конфликт) или спросить пользователя.
- Несколько задач в одном запросе — отдельная ветка и коммит на каждую; не смешивать.

**2. Завершение задачи** — только после выполнения `acceptance.md` (`npm run accept` = 0 и APPROVE, где ревью требуется) и после обновления памяти:
- `bash scripts/git-task.sh commit "<type(scope): описание>" -- <файлы задачи, включая .ai/memory/…>`.
- Один коммит на задачу; перечислять файлы явно, `git add -A` запрещён.
- Приёмка красная / ревью не пройдено / задача осталась «В работе» → **не коммитить** (WIP-коммиты не делаются).
- Коммит делается на ветке задачи. Push, PR и слияние в `develop` — только по просьбе.
- В отчёте указать ветку и хеш коммита.

## Ветки
| Ветка | Откуда | Куда сливается | Назначение |
|---|---|---|---|
| `main` | — | — | Всегда стабильная, готова к релизу; только релизы и hotfix |
| `develop` | `main` | `release/*` | Интеграционная ветка; сюда сливаются готовые фичи |
| `feature/<id>-<slug>` | `develop` | `develop` | Одна задача, например `feature/FE-02-send-message` |
| `release/<x.y.z>` | `develop` | `main` и `develop` | Стабилизация релиза: только багфиксы, версия, документация |
| `hotfix/<x.y.z>-<slug>` | `main` | `main` и `develop` | Срочное исправление продакшена |
| `bugfix/<id>-<slug>` | `develop` | `develop` | Некритичный баг вне релиза |

- Прямые коммиты в `main` и `develop` запрещены (исключение — коммиты слияния).
- Имя ветки: латиница, нижний регистр (кроме `FE-NN`), слова через `-`. `<id>` — номер задачи из `tasks.md`.
- Новая работа начинается с актуальной `develop`: `git switch develop && git pull && git switch -c feature/FE-NN-slug`.
- `develop` при отсутствии создаётся скриптом локально (см. «Автоматический цикл»); на удалённый репозиторий не пушится без просьбы.
- Добавлен вспомогательный тип `chore/<slug>` (от `develop` в `develop`) для работы вне бэклога.

## Слияние
- `feature/*`, `bugfix/*` → `develop` через PR, `--no-ff`. Условие: `npm run accept` = 0 **и** APPROVE от `react-reviewer` (`acceptance.md`).
- `release/*` и `hotfix/*` → `main` с `--no-ff`, затем тег `vX.Y.Z` на `main`, затем слияние обратно в `develop`.
- После слияния ветка `feature/*` / `bugfix/*` / `release/*` / `hotfix/*` удаляется (только после подтверждения, что слияние прошло).
- Версионирование — SemVer: `MAJOR.MINOR.PATCH`. Теги аннотированные: `git tag -a vX.Y.Z -m "Release X.Y.Z"`.

## Сообщения коммитов (Conventional Commits)
Формат: `<type>(<scope>): <описание>`; scope необязателен.

- `type`: `feat` · `fix` · `refactor` · `test` · `docs` · `style` · `perf` · `build` · `ci` · `chore` · `revert`.
- `scope` — модуль или слайс: `chats`, `login`, `messages`, `join-form`, `store`, `e2e`.
- Описание: повелительное наклонение, до ~72 символов, без точки в конце. Язык — русский (как в проекте); идентификаторы и команды — как в коде.
- Тело (опционально, через пустую строку): **зачем** изменение, а не что — это видно из диффа.
- Ссылка на задачу — в тексте или футере: `Refs: FE-02`.
- Breaking change: `!` после типа/scope и футер `BREAKING CHANGE: ...`.
- Футер атрибуции агента добавляется последней строкой, если его требует окружение Claude Code.

Примеры:
```
feat(messages): отправка сообщения из Dialog по Enter

Refs: FE-02
```
```
fix(login): инвертировать условие показа формы входа
```
```
test(chats): тесты слайса chats до реализации счётчика участников
```

## Чек-лист перед коммитом
1. Задача завершена: `npm run accept` = 0, ревью APPROVE (если требуется). Для не-автоматических коммитов (WIP, amend и т.п.) — пользователь попросил.
2. Ветка корректна (не `main`/`develop` для обычной работы).
3. Память обновлена, `check-memory.sh` = 0.
4. Staged-diff проверен, лишнего и секретов нет.
5. Сообщение соответствует формату выше.
