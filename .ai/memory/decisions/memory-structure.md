# Решения: Память проекта: раскладка и порядок

Формат записи и правила — `../decisions.md`. Записи до FE-D51 перенесены из исходного `decisions.md` без изменений.

## SH-D01 — AI-память хранится в `.ai/memory/` в репозитории (2026-10-04)
- **Решение:** `CLAUDE.md` в корне + markdown-файлы в `.ai/memory/`, коммитятся в git.
- **Почему:** общий контекст между сессиями и разработчиками, версионируется вместе с кодом.

## SH-D03 — Память разделена на frontend/backend + общий контракт (2026-10-04)
- **Решение:** отдельные `state/tasks/decisions/architecture` для каждой стороны в папках frontend/ и backend/ внутри памяти, общие файлы contracts.md и decisions.md; владение файлами по стороне; проверка структуры `scripts/check-memory.sh` в составе `npm run accept`.
- **Почему:** параллельная разработка frontend и backend без конфликтов правок памяти; отчёты агентов строятся из актуальных файлов своей стороны; механическая проверка защищает от устаревших/битых записей.
- **Альтернативы:** один общий набор файлов (конфликты при параллельной работе, смешение задач); монорепо-пакеты с отдельными CLAUDE.md (преждевременно, пока бэкенда нет).

## SH-D11 — Память: плоская раскладка `.ai/memory/` без подпапки `frontend/`, один `decisions.md` (2026-10-05)
- **Решение:** файлы `state/tasks/architecture/auth-contract.md` перенесены из подпапки `frontend/` в `.ai/memory/`; `frontend/decisions.md` слит в общий `decisions.md` (FE-D01…FE-D06 сохранили ID, добавлены после SH-D10). Меняет формат из SH-D04 (подпапка `frontend/`); ID задач `FE-NN` и решений `FE-Dxx` не менялись. `check-memory.sh` и `git-task.sh` читают плоские пути. Старые пути в прежних записях `tasks.md`/`decisions.md` исторические, не правятся.
- **Почему:** сторона в проекте одна (SH-D04), подпапка и два файла решений с разными префиксами только путали и порождали коллизию имён `decisions.md`.
- **Альтернативы:** оставить два файла (`decisions.md` + `fe-decisions.md`) — два места для решений; свести `tasks/state/architecture` в корень, а контракты и соглашения (`auth-contract`, `product-agreements`) — в подпапку (не выбрано).

## FE-D50 — Удаление `auth-contract.md` (2026-10-18)
- **Решение (выбор пользователя):** файл `auth-contract.md` удалён целиком; уточняет FE-D39 (вместо строки-указателя — удаление). Источник истины по auth — `docs/client-integration.md` §2 (FE-D12); история FE-09 → FE-D12 сохранена в `decisions-archive.md` и git.
- **Почему:** файл был заглушкой («заменён, новое сюда не вносить»): таблица «где искать» дублировала оглавление контракта, а различия FE-09 и FE-D12 уже описаны в решении FE-D12.
- **Альтернативы (не выбраны):** оставить одну строку-указатель на спеку (FE-D39).

## FE-D51 — `decisions.md` — роутер, тексты решений по темам в `decisions/*.md` (2026-10-18)
- **Решение:** файл решений (303 строки, ~90 КБ) разнесён на 17 тематических файлов `.ai/memory/decisions/<тема>.md` по 2–12 КБ; `decisions.md` содержит только шаблон записи и таблицы-роутер (`ID | название | статус | файл`) по темам. Тексты решений перенесены без изменений. Новое решение добавляется в конец профильного файла темы и строкой в таблицу роутера; `scripts/check-memory.sh` проверяет, что для каждого решения есть строка роутера с верным файлом, ID уникальны (в том числе с `decisions-archive.md`), каждый файл `decisions/` упомянут в роутере. Заменённое («ЗАМЕНЕНО») по-прежнему переносится в `decisions-archive.md`, строка роутера удаляется. Развивает FE-D41.
- **Почему:** выбор пользователя: читать нужное решение без загрузки всего объёма; поиск по заголовкам с нарезкой по строкам был неудобен. Пользователь выбрал более мелкую раскладку, чем предложенные 7 файлов.
- **Альтернативы:** 7 крупных файлов (отклонено в пользу более мелких); один файл с оглавлением (не снижает объём чтения); оставить как есть и искать по заголовкам.

## FE-D52 — Архив `done.md` — роутер, записи по одной в `done/<ID>.md` (2026-10-18)
- **Решение (выбор пользователя):** архив закрытых задач (57 КБ, 73 записи) разносится на файлы `.ai/memory/done/<ID>.md` (несколько записей одного ID — в одном файле; записи без ID — `done/<ГГГГ-ММ-ДД>-<слаг>.md`), тексты записей переносятся слово в слово. `done.md` остаётся роутером: таблица `Дата | ID | Суть | Файл`, новая строка добавляется в конец при закрытии задачи. Архив остаётся в `.ai/memory/` (не переносится в `docs/`). Уточняет FE-D27 (место архива) и FE-D35 (поле «Кейсы:» читается из `done/<ID>.md`).
- **Почему:** файл читали целиком (~20K токенов) ради одной записи; скрипты (`check-state.js`, `check-memory.sh`) и так находят запись по ID, а файл на задачу даёт поиск по имени без регулярок и без конфликтов при слиянии, как у `backlog/FE-NN.md`. Проверки и ссылки памяти работают в `.ai/memory/`, перенос в `docs/` размер бы не уменьшил.
- **Альтернативы:** разбивка по эпикам/темам (отклонено: запись относится сразу к нескольким темам, а по ID всё равно нужен роутер); разбивка по месяцам (отклонено: вся история в одном месяце); перенос в `docs/` (отклонено: не снижает размер, рвёт проверки памяти); оставить один файл.

## FE-D53 — Лимит «Бэклога» в tasks.md и очередь queue.md (2026-10-18)
- **Решение (выбор пользователя):** в «Бэклоге» `tasks.md` не больше 7 строк задач (лимит считается только по «Бэклогу», «В работе» отдельно). Остальные задачи лежат в `.ai/memory/queue.md`, который при работе не читается. Новая задача: если в «Бэклоге» есть менее приоритетная, наименее приоритетную (с наибольшим P; при равном — последнюю в списке) переносят в конец `queue.md`, новую кладут в `tasks.md`; иначе (равный приоритет не вытесняется) новую дописывают в конец `queue.md` без чтения файла. Когда в «Бэклоге» остаётся меньше 3 задач, `queue.md` читают и подтягивают задачи по приоритету (P1, P2…; при равном — по порядку в файле) до 7 или пока очередь не опустеет. Формат строк и подробности `backlog/FE-NN.md` не меняются. `scripts/check-memory.sh` проверяет лимит, наличие `(P<число>…` у каждой строки, инвариант «худший P в `tasks.md` не ниже лучшего P в `queue.md`», необходимость пополнения, уникальность ID по обоим файлам. Развивает FE-D41.
- **Почему:** `tasks.md` читают при каждой задаче, и 54 строки бэклога расходуют токены на старте впустую; приоритетные 7 задач достаточно для выбора следующей.
- **Альтернативы (отклонены пользователем):** считать лимит вместе с «В работе»; пополнять «Бэклог» фиксированной порцией.
