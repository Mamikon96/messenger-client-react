# Паттерны и архитектурные правила проекта
Читать: при проектировании и реализации компонента, слайса, сервиса, хука; обязательно при ревью (`react-reviewer`). Общие паттерны и антипаттерны — скилл `react-patterns`; здесь только то, что специфично для проекта. Конфликт с `decisions.md` решается в пользу `decisions.md`.

## Слои и зависимости
Направление импортов: `modules/*` (UI) → `reducers/*` (слайсы, thunks, селекторы) → `services/*` → сеть. Обратные импорты запрещены: `services/` и `reducers/` не импортируют из `modules/`; `store.js` импортирует слайсы, слайсы не импортируют `store.js`.
- `src/app/services/` — единственное место HTTP и преобразования ответов в клиентскую модель (`apiClient.js`, `authApi.js`). Компоненты не вызывают `fetch` напрямую.
- `src/app/reducers/` — состояние и переходы. Побочные эффекты — только в thunks (`createAsyncThunk`), редьюсеры чистые.
- `src/app/modules/<module>/` — UI. Вложенные части лежат в `components/<name>/` и импортируются только своим модулем.
- `src/app/modules/ui/` — общие примитивы (`Button`, `IconButton`, `Input`, `Avatar`): без знания о store и доменных сущностях, стили только на токенах (FE-D07). Повторяющуюся разметку выноси сюда, а не копируй.
- Внешнее состояние вне Redux (тема — FE-D08) оформляется отдельным модулем с `subscribe`/`getSnapshot` и хуком на `useSyncExternalStore`; добавлять новые такие хранилища — по согласованию.

## Состояние
- Один источник истины. Выбранная сущность хранится идентификатором (целевая модель — `activeChatId`, FE-37); текущая копия в `activeChat` — известный долг, новый код ей не подражает.
- Компоненты читают данные через селекторы, экспортируемые из файла слайса; путь в state в компонентах не пишется. Подписка — на минимальный срез.
- Асинхронный процесс описывается статусом (`loading`/`authenticated`/`error` и т. п., как в `auth`), а не набором булевых флагов.
- В store только сериализуемые данные. Локальное UI-состояние (открыт ли popover, значение поля формы) остаётся в компоненте.
- Данные API приводятся к клиентской модели в `services/`/thunk; компоненты не разбирают сырой ответ.

## Компоненты
- Логика получения данных и действий — в хуке или селекторе/thunk; компонент отвечает за разметку и связывание событий. Обработчик, разросшийся за пару строк, выносится.
- Состояния loading/empty/error обязательны для всего, что зависит от асинхронных данных.
- Ошибки API показываются по `error.code` (`ApiError`), а не по тексту сообщения; тексты — в одном месте (`authError.js` как образец).
- Компонент не знает внутренности чужого модуля: общение через props, store или публичный экспорт.

## Что считать нарушением при ревью
Серьёзность — по разделу 8 скилла `react-patterns`. Для проекта дополнительно:
- 🔴 `fetch`/XHR вне `services/`; вызов API из редьюсера; импорт `modules/*` из `services/` или `reducers/`; новая библиотека/подход без записи в `decisions.md` (`tech-approval.md`).
- 🟠 Дубль состояния или копия сущности вместо id; компонент с путём в state вместо селектора; новый компонент, дублирующий примитив из `ui/`; бизнес-логика в JSX; булевы флаги вместо статуса; нет loading/empty/error.
- 🟡 Хук/селектор без осмысленного имени; абстракция под единственный случай.
Известные долги (не считать новой виной автора, но не расширять): `activeChat` как копия чата; `Form.js` — мёртвый код (FE-05).
