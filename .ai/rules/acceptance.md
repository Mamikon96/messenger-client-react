# Приёмка задач
Читать: когда задача реализована и нужно решить, можно ли её закрыть.
Источник: FE-D17, FE-D23, FE-D29, FE-D35, FE-D36, FE-D48; гейты исполняют `scripts/accept.sh`, `scripts/qa-required.sh`, `scripts/check-state.js --require-qa`. Пересмотреть, когда меняется один из этих скриптов или решение.

В «Сделано» (архив `.ai/memory/done/<ID>.md` + строка в роутере `.ai/memory/done.md`) — только при выполнении условий:
1. `npm run accept` → код 0 (`scripts/accept.sh`: память, кейсы ↔ API ↔ код, ESLint без предупреждений, тесты чекера, unit, e2e; при успехе пишет штамп `.qa/accept.json`; `bash scripts/accept-stamp.sh check` — действителен ли он для текущих файлов; ревьюер тестов не запускает и судит по штампу, FE-D35).
2. Ревьюер `react-reviewer` вынес **APPROVE** по текущему коду (ревью — после зелёной приёмки).
3. Если задача меняет поведение приложения (код или стили в `src/`, `mock-bff/`; только `*.test.js`/`setupTests.js` — не считается, FE-D29; правило — `scripts/qa-required.sh`): агент `qa-tester` (FE-D17) прошёл в браузере объём `node scripts/check-state.js --qa-scope` — active-кейсы из поля «Кейсы» контракта плюс smoke (`QA_SMOKE` в `scripts/check-state.js`), FE-D35 — и сам записал свежий отчёт `.qa/runs/<задача>.md` (путь — `node scripts/check-state.js --qa-report-path`, FE-D36) со строкой `Объём:` и `Вердикт: PASS` (нет открытых BLOCKER/MAJOR). Остальные active-кейсы покрывает полный e2e из `npm run accept`. Проверка — `bash scripts/check-state.sh --require-qa`; её автоматически делает `scripts/git-task.sh commit`.

## Порядок: от дешёвого к дорогому (FE-D35)
Каждый следующий гейт запускается только после зелёного предыдущего:
1. **Итерация разработки:** правка → `bash scripts/check-fast.sh` (только затронутые изменениями проверки) — до зелёного.
2. **Приёмка:** `npm run accept` — один раз, полная регрессия, штамп.
3. **Ревью** `react-reviewer` — читает diff и контракт, тестов не запускает (штамп). Лёгкий трек (FE-D41): P3 без изменения поведения (`Кейсы: нет`) — ревью на модели sonnet; QA — по общим правилам п. 3 (FE-D29).
4. **QA** `qa-tester` — только после APPROVE ревью (если п. 3 применим); не параллельно с ревью: замечание ревью меняет код и обнуляет браузерный проход.
- `REJECT`/`APPROVE WITH FIXES` → исправить все BLOCKER и MAJOR → шаги 1–3 (повторное ревью) → QA.
- `FAIL` QA → исправить все BLOCKER и MAJOR → шаги 1–2 → повторное ревью **только diff исправления** → повторный QA в том же объёме.
- Всё зелёное → запись в «Сделано» (файл `done/<ID>.md` и строка роутера) с пометкой `ревью: react-reviewer APPROVE`.
Ревьюер и `qa-tester` получают в промпте контракт задачи (`task-contract.md`) и судят по нему: невыполненная «Проверка задачи» или изменения вне скоупа — замечание.
Субагенты других агентов не запускают: ревью запускает основная сессия. Ревью не пройдено — задача остаётся «В работе» с пунктом «Осталось: ревью».
Изменения только конфигов/процесса/документации — ревью не требуется (отметить это в записи).
После записи в «Сделано» (и обновления памяти) — автоматический коммит на ветке задачи по `.ai/rules/git-flow.md`. Без выполненной приёмки коммит не делается.

## Лимит раундов (FE-D23)
- Ревью или QA второй раз подряд возвращают замечание по одной и той же причине → остановиться, записать строку в `.ai/memory/failures.md` (симптом, слой) и спросить пользователя: неясен контракт или правило не механизировано.
- Больше 2 раундов «REJECT/FAIL → исправление» по задаче → то же самое. Третий раунд без решения пользователя не запускается.
- Любой REJECT ревьюера и FAIL QA — строка в `failures.md`.

## Адрес бэкенда при приёмке
- Реальный бэкенд (`messenger-server`) доступен на порту **3333**, если в переменных окружения адрес не задан (`BACKEND_URL` не установлен): `src/setupProxy.js` проксирует `/api` на `http://localhost:3333`.
- Mock-BFF по умолчанию слушает порт **3334** (`MOCK_BFF_PORT`, `DEFAULT_PORT` в `mock-bff/server.js`, FE-81), поэтому `npm run accept` работает при запущенном реальном бэкенде. Если 3334 занят — ошибка запуска, а не молчаливый прогон на чужом сервере.
- Playwright e2e из `npm run accept` идут на mock-BFF (`playwright.config.js`: `BACKEND_URL` задаётся для dev-сервера e2e).
- Проход `qa-tester` — на mock-BFF `http://localhost:3334` (`.claude/agents/qa-tester.md`); ручная проверка с реальным бэкендом — `http://localhost:3333`, если `BACKEND_URL` не задан.

## Цикл тестировщика (qa-tester)
- Запускает основная сессия после APPROVE ревью (субагенты агентов не запускают); в промпт — контракт задачи и вывод `node scripts/check-state.js --qa-scope`. Задача определяется по имени ветки (`feature/FE-NN-…`): кейсы берутся из её контракта в «В работе», а после переноса в «Сделано» — из поля «Кейсы:» её записи в `done/<ID>.md` (FE-D52, `memory-protocol.md`). Агент сам поднимает приложение, проходит кейсы руками (Playwright MCP — проход; Chrome DevTools MCP — повтор проблемных кейсов для диагностики, FE-D43), код не правит; результат — `.qa/runs/<задача>.md` (вне git: `.qa/` в `.gitignore`), агент пишет его сам. Ошибка записи отчёта у `qa-tester` — стоп и вопрос пользователю; основная сессия отчёт за агента не сохраняет (FE-D36).
- `Вердикт: FAIL` → отчёт передаётся `react-engineer` на исправление **всех** BLOCKER и MAJOR → порядок выше → **повторный** проход `qa-tester` в том же объёме. Старый отчёт устаревает сам: в нём хэш кода и хэш кейсов (`node scripts/check-state.js --tree-hash`).
- Кейс нельзя пройти (`blocked`) или он неясен — вопрос пользователю, не допущение. Playwright e2e из приёмки не убирается: агент его дополняет (FE-D17).
- Изменения только конфигов/процесса/документации — проход тестировщика не требуется (отметить в записи).

## Экономия токенов qa-tester (FE-D47)
- По умолчанию `qa-tester` — модель sonnet (`.claude/agents/qa-tester.md`). Для особо рискованной задачи (общая инфраструктура, авторизация) основная сессия может запустить его с `model: opus`.
- Кейсы про отказы сети, ретраи и тайминги `qa-tester` не проходит в браузере: в матрице `pass (e2e)` с указанием e2e-теста с тегом `[UC-…]`; `--require-qa` принимает отметку только при наличии такого теста (FE-D48).
- Скриншоты агент не открывает через `Read`, делает их только при `fail`; есть бюджет ходов (~60 на проход), при превышении — стоп и отчёт `blocked`.
