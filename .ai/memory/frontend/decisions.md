## FE-D01 — Redux Toolkit для состояния (до 2026-10-04, зафиксировано из кода)
- **Решение:** глобальное состояние в RTK-слайсах (`chats`, `activeChat`, `users`), id генерируются `nanoid()` на клиенте.
- **Почему:** нет бэкенда; RTK — стандарт для Redux.
- **Альтернативы:** Context/useReducer (не выбраны, причины не зафиксированы).

## FE-D02 — Структура «модуль = папка с компонентом и CSS» (зафиксировано из кода)
- **Решение:** `app/modules/<name>/Name.js + Name.css`, вложенные части в `components/`; БЭМ-классы с модификаторами `_x`.
- **Почему:** локальность стилей и кода без CSS-in-JS.

## FE-D03 — Процесс: память после любых изменений и согласование технологий (2026-10-05)
- **Решение:** (1) после любых изменений, до ответа пользователю, актуализируется `tasks.md` (и при необходимости `state.md`/`architecture.md`, штамп); (2) новая технология, библиотека или подход применяются только после опроса пользователя, а запись в decisions — только после его согласия; (3) `scripts/check-memory.sh` падает, если изменённые относительно HEAD файлы кода (`src/`, `e2e/`, `scripts/`, `package.json`, `playwright.config.js`) новее `frontend/tasks.md`.
- **Почему:** требование владельца проекта: память всегда актуальна, а выбор технологий остаётся за ним; проверка по времени изменения даёт механическую защиту от забытых обновлений.
- **Альтернативы:** обновлять память только по завершении задачи (риск устаревших данных между этапами); записывать решения автоматически (отвергнуто — решает владелец); проверка свежести через хук коммита (не выбрано: сложнее и срабатывает позже).

## FE-D04 — Авторизация: OAuth Google/GitHub через BFF с httpOnly-cookie сессией (2026-10-05)
- **Решение:** (1) вход только через OAuth Google/GitHub к своему API (бэкенд отдельный, пока не существует; контракт фиксируется заранее, на фронте мокается); email+пароль, passkeys, 2FA не делаем. (2) Архитектура BFF: кнопка провайдера делает полную навигацию на `/api/auth/{provider}/start`, код меняет сервер (state + PKCE), сессия хранится в cookie `HttpOnly; Secure; SameSite=Lax`, изменяющие запросы несут CSRF-заголовок. (3) Топология: SPA и API на одном сайте, только веб, других клиентов нет. (4) Фронт: слайс `auth` (`status` + `user`), единый apiClient с глобальной обработкой 401, сброс всего store при logout; в Redux и localStorage нет токенов и csrfToken; `loginService`/ключ `user` в localStorage уходят. (5) Без роутера: гейт по `auth.status` в `src/App.js`. (6) Мок M3 + M1: в Jest — подмена fetch/`authApi`, в Playwright — `page.route`, плюс локальный Node mock-BFF через CRA proxy для dev и e2e (затрагивает `playwright.config.js` и `scripts/accept.sh`).
- **Почему:** BFF — рекомендация RFC 10017 для приложений с персональными данными, и токены не попадают в JS; самый простой и тестируемый фронт, без новых пакетов; один сайт и отсутствие других клиентов снимают главный минус cookie-сессии; mock-BFF даёт настоящие редиректы, httpOnly-cookie и 401, близко к бою.
- **Альтернативы:** B — access в памяти + refresh-cookie с ротацией (отклонён: по RFC слабее BFF, сложный фронт — single-flight refresh, гонки между вкладками; нужен только для разных доменов или многих клиентов); C — только контракт + фейковый authApi (отклонён: не проверяет редиректы, cookie, 401 и CSRF, решение просто откладывается); MSW (отклонён: не эмулирует httpOnly-cookie и навигации, несовместим с Jest 27 в CRA без обходов, 3.0 слишком свежий); react-router-dom@7 (отклонён: сейчас не нужны URL и deep-links, достаточно гейта; v8 несовместим с React 18).

## FE-D05 — Авторизация: dev-прокси, контракт auth API, CSRF и истечение сессии (2026-10-05)
- **Решение:** уточняет FE-D04. (1) Dev-прокси — файл src/setupProxy.js (будет создан) на `http-proxy-middleware` 2.x, явно в devDependencies. (2) Контракт auth API ведётся Markdown-документом в `.ai/memory/frontend/` (не OpenAPI). CSRF-токен фронт получает из тела ответа `GET /api/auth/session`, хранит только в модуле apiClient (не в Redux и не в localStorage), отправляет в заголовке `X-CSRF-Token`. (3) Истечение сессии (401): сразу переход в `anonymous`, сброс store, экран входа с сообщением «сессия истекла»; черновик и открытый чат не сохраняются.
- **Почему:** поле `proxy` в package.json не проксирует навигацию (`Accept: text/html`), а `/api/auth/{provider}/start` — это полная навигация; явная зависимость не ломается при обновлении react-scripts. Markdown-контракт и токен в теле `/session` — выбор пользователя, без лишних инструментов. Простое поведение при 401 — выбор пользователя.
- **Альтернативы:** транзитивная копия `http-proxy-middleware` из react-scripts (хрупко); свой Node-прокси, объединяющий SPA и mock-BFF (сложнее); OpenAPI-файл для контракта; CSRF по схеме double-submit через читаемую cookie; модалка «войдите снова» с сохранением черновика.

## FE-D06 — Авторизация: поля user, срок сессии, сигнал ошибки OAuth (2026-10-05)
- **Решение:** уточняет FE-D04/FE-D05. (1) `user` в ответе `GET /api/auth/session` — `id`, `name`, `avatarUrl`, `provider`; email не передаётся. (2) Срок сессии — только абсолютный, 7 дней; idle-таймаута и «запомнить меня» нет. (3) Ошибка OAuth после callback — редирект на `/?auth_error=<код>` (`access_denied`, `provider_error`, `invalid_state`); фронт показывает сообщение и чистит URL через `history.replaceState`. Контракт целиком — `auth-contract.md`.
- **Почему:** минимальный набор данных профиля (меньше персональных данных); абсолютный срок проще для сервера; параметр в URL работает без роутера (FE-D04).
- **Альтернативы:** `user` с email (больше персональных данных, нужен только для связывания аккаунтов); idle 30 минут + абсолютный срок 7 дней; срок не фиксировать в контракте; ошибка OAuth через одноразовую временную cookie, отдаваемую `/api/auth/session` (сложнее).
