## SH-D01 — AI-память хранится в `.ai/memory/` в репозитории (2026-10-04)
- **Решение:** `CLAUDE.md` в корне + markdown-файлы в `.ai/memory/`, коммитятся в git.
- **Почему:** общий контекст между сессиями и разработчиками, версионируется вместе с кодом.

## SH-D02 — Приёмка задач через `npm run accept` (2026-10-04)
- **Решение:** задача завершена только при зелёных unit (Jest/RTL через react-scripts) и e2e (Playwright, chromium, dev-сервер на порту 3100). Единая точка входа — `scripts/accept.sh`.
- **Почему:** требование владельца проекта; один детерминированный критерий готовности.
- **Альтернативы:** Cypress (тяжелее), отдельные команды без общего скрипта (легко забыть e2e).
- **Примечание:** покрывает frontend (единственная сторона проекта, см. SH-D04).

## SH-D03 — Память разделена на frontend/backend + общий контракт (2026-10-04)
- **Решение:** отдельные `state/tasks/decisions/architecture` для каждой стороны в папках frontend/ и backend/ внутри памяти, общие файлы contracts.md и decisions.md; владение файлами по стороне; проверка структуры `scripts/check-memory.sh` в составе `npm run accept`.
- **Почему:** параллельная разработка frontend и backend без конфликтов правок памяти; отчёты агентов строятся из актуальных файлов своей стороны; механическая проверка защищает от устаревших/битых записей.
- **Альтернативы:** один общий набор файлов (конфликты при параллельной работе, смешение задач); монорепо-пакеты с отдельными CLAUDE.md (преждевременно, пока бэкенда нет).

## SH-D04 — Backend исключён из проекта, остаётся только frontend (2026-10-05)
- **Решение:** удалены `backend/` и `contracts.md` из памяти; в проекте одна сторона — frontend (папка `frontend/`, ID `FE-`). Решение SH-D03 в части backend/contracts утратило силу; в `check-memory.sh` убраны проверки backend. Формат с подпапкой `frontend/` сохранён, чтобы протокол `project-memory` работал без изменений.
- **Почему:** бэкенд в этом репозитории не нужен (владелец проекта); заглушки без содержимого вводили в заблуждение и требовали поддержки.
- **Альтернативы:** вернуть плоскую раскладку без `frontend/` (ломает единый протокол скилла, который ожидает подпапку стороны).

## SH-D05 — Решение фиксируется сразу после выбора пользователя; пишет solution-architect (2026-10-05)
- **Решение:** после ответа пользователя на `AskUserQuestion` решение с обоснованием («Решение / Почему / Альтернативы») записывается в `decisions.md`: если варианты готовил `solution-architect` — он сам (ему выдан `Edit` только для `decisions.md`, основная сессия передаёт ему выбор через `SendMessage`), иначе основная сессия. Уточняет FE-D03: согласием на запись считается сам выбор, запись не откладывается до конца реализации.
- **Почему:** агенты читают готовые решения и не изобретают их заново; причины фиксируются, пока свежи, а не после реализации; архитектор лучше всех знает, почему отклонены альтернативы.
- **Альтернативы:** запись основной сессией после реализации (прежний порядок — решения теряются или теряют контекст); отдельный вопрос «записывать ли?» (лишний шаг, выбор уже есть).

## SH-D06 — Жёсткое правило для всех агентов: сомнение или нехватка данных → вопрос пользователю (2026-10-05)
- **Решение:** любой агент при сомнении или нехватке данных спрашивает пользователя и ничего не придумывает (требования, поведение, значения, причины багов, факты о коде). Правило в `.ai/rules/ask-user.md`, п. 6 «Неснимаемых правил» `CLAUDE.md`, блок «Жёсткое правило» в каждом агенте `~/.claude/agents/*`. Агент без `AskUserQuestion` (ревьюеры, фоновые) возвращает вопросы вызывающему, основная сессия переадресует их пользователю.
- **Почему:** догадки агентов дают неверные требования и незаметные ошибки; цена вопроса ниже цены переделки.
- **Альтернативы:** правило только в `CLAUDE.md` (агенты вне проекта его не увидят); допущения «по умолчанию» с пометкой в отчёте (всё равно строит работу на выдумке).

## SH-D07 — PR создаётся автоматически после коммита задачи; ветка удаляется автоматически после слияния (2026-10-05)
- **Решение:** после `git-task.sh commit` агент сам пушит ветку и создаёт PR в `main` (пока нет `develop` в `origin`), без строки «Generated with Claude Code» в описании. Слияние и теги — по-прежнему только по просьбе. В репозитории включено «Automatically delete head branches»; `develop` и `release/*` защищены ruleset `protect-develop-release` (запрет удаления). Меняет прежнее «push и PR — только по просьбе» в `git-flow.md`.
- **Почему:** владелец проекта хочет, чтобы цикл задачи доходил до PR без лишних просьб, а ветки не копились. У GitHub нет галочки удаления при создании PR (есть только при слиянии), поэтому надёжнее настройка репозитория, чем флаг в каждой команде.
- **Альтернативы:** `gh pr merge --delete-branch` только при слиянии вручную (не работает при слиянии кнопкой в вебе); `gh pr merge --auto --delete-branch` при создании PR (требует auto-merge и противоречит правилу «слияние только по просьбе»).

## SH-D08 — Ветка `develop` опубликована в `origin`; PR задач идут в `develop` (2026-10-05)
- **Решение:** `develop` создана от `main` (e4827d4) и запушена в `origin` по просьбе пользователя. База PR для `feature/*`, `bugfix/*`, `chore/*` — `develop`; `release/*` и `hotfix/*` — `main`. Уточняет SH-D07 (там база `main`, «пока нет `develop`»).
- **Почему:** git-flow проекта (`git-flow.md`) предполагает интеграционную ветку; `develop` защищена ruleset `protect-develop-release` от удаления.
- **Альтернативы:** оставить PR в `main` (противоречит git-flow, `main` должна быть только релизной).

## SH-D09 — Продукт: реальный мессенджер для малой закрытой группы, бэкенд — отдельный проект (2026-10-05)
- **Решение:** цель — реальный продукт (общение людей в реальном времени) для малой закрытой группы: до ~1 000 пользователей, один сервер, шифрование на транспорте (TLS), без E2EE. Бэкенд делается в **отдельном проекте/репозитории**; этот репозиторий остаётся frontend (SH-D04 не отменяется). Все соглашения по продукту, архитектуре и бэкенду — в `.ai/memory/product-agreements.md`; после создания проекта бэкенда работа продолжится там, а файл послужит входными данными.
- **Почему:** владелец проекта хочет настоящий мессенджер, а не демо; отдельный репозиторий не смешивает релизные циклы и процессы двух сторон.
- **Альтернативы:** клиент под внешний бэкенд на mock-BFF (не даёт реального продукта); учебный/портфолио-проект (не соответствует цели); публичный продукт с ростом, E2EE и корпоративный вариант (избыточны для малой группы, сильно усложняют архитектуру).

## SH-D10 — Основа бэкенда: Node.js + WebSocket + PostgreSQL (2026-10-05)
- **Решение:** собственный сервер на Node.js, реалтайм через WebSocket, данные в PostgreSQL. Продолжает контракт BFF/OAuth из `frontend/auth-contract.md`. Конкретные библиотеки (фреймворк, драйвер БД, WebSocket-слой) согласуются отдельно в проекте бэкенда по `tech-approval.md`.
- **Почему:** максимальный контроль и совместимость с уже зафиксированным контрактом auth; для ~1 000 пользователей объём бэкенда невелик; PostgreSQL даёт запас роста (индексы, полнотекстовый поиск, LISTEN/NOTIFY).
- **Альтернативы:** BaaS (Supabase/Firebase) — быстрый старт, но привязка к вендору и пересмотр контракта auth; Matrix (Synapse) — бэкенд не нужен, но тяжёлая модель протокола и контракт auth почти не нужен; «только клиент на mock-сервере» — не даёт реального продукта.
