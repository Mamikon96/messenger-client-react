# Решения: Приёмка и контракт задачи

Формат записи и правила — `../decisions.md`. Записи до FE-D51 перенесены из исходного `decisions.md` без изменений.

## SH-D02 — Приёмка задач через `npm run accept` (2026-10-04)
- **Решение:** задача завершена только при зелёных unit (Jest/RTL через react-scripts) и e2e (Playwright, chromium, dev-сервер на порту 3100). Единая точка входа — `scripts/accept.sh`.
- **Почему:** требование владельца проекта; один детерминированный критерий готовности.
- **Альтернативы:** Cypress (тяжелее), отдельные команды без общего скрипта (легко забыть e2e).
- **Примечание:** покрывает frontend (единственная сторона проекта, см. SH-D04).

## FE-D20 — Контракт задачи до кода с механической проверкой (2026-10-12)
- **Решение:** при переносе задачи в «В работе» основная сессия пишет контракт подпунктами под задачей: Цель, Кейсы, Проверка задачи, В скоупе, Вне скоупа, Открытые вопросы, Осталось (формат — `.ai/rules/task-contract.md`). Тесты и код не начинаются, пока открытые вопросы не закрыты пользователем. Наличие и непустоту полей проверяет `scripts/check-contract.sh` из `scripts/check-memory.sh` (тесты — `scripts/check-contract.test.js`, входят в `npm run accept`).
- **Почему:** выбор пользователя по аудиту харнеса (`docs/ai-harness-audit.md`, P1.1). Критерий «`npm run accept` = 0» у задач общий и не проверяет выполнение конкретной задачи; расхождение с постановкой выявлялось только на ревью/QA, через полный цикл итераций. Механическая проверка не даёт правилу забыться.
- **Альтернативы:** правило только текстом в `.ai/rules/` без проверки скриптом — дешевле, но держится на дисциплине агента («правило вместо проверки» — антипаттерн по Harness_ru); не выбрано.

## FE-D23 — Лимит раундов ревью/QA и журнал провалов (2026-10-12)
- **Решение:** повтор замечания ревью/QA по одной причине второй раз подряд или больше 2 раундов «REJECT/FAIL → исправление» — остановка, строка в `.ai/memory/failures.md` и вопрос пользователю (`.ai/rules/acceptance.md`, «Лимит раундов»). Любой REJECT/FAIL записывается в журнал; повторяющееся замечание превращается в проверку, а текстовое правило о нём удаляется.
- **Почему:** выбор пользователя по аудиту харнеса (P1.3, P3.2): бесконечные циклы исправлений тратят токены и обычно означают дефект постановки или нехватку механической проверки, а не ошибку реализации.
- **Альтернативы:** ввести позже, отдельно от контракта; не выбрано.

## FE-D29 — QA-проход обязателен только при изменении кода или стилей приложения (2026-10-13)
- **Решение:** уточняет FE-D17: `git-task.sh commit` требует свежий отчёт `qa-tester` с PASS, только если среди файлов коммита есть код или стили в `src/` или `mock-bff/`. Файлы `*.test.js` и `setupTests.js` поведение приложения не меняют и QA не требуют. Правило вынесено в `scripts/qa-required.sh` (тесты — `scripts/qa-required.test.js`, входят в `npm run accept`).
- **Почему:** выбор пользователя при закрытии FE-49: задача меняла только unit-тесты в `src/`, а прежний гейт требовал ручной проход всех кейсов в браузере (больше часа) без пользы для проверки поведения; ревью и приёмка такие изменения покрывают.
- **Альтернативы:** повторный QA-проход без изменения правил; разовый коммит в обход гейта с пометкой в памяти; не выбраны.

## FE-D35 — Каскад проверок от дешёвых к дорогим (2026-10-13)
- **Решение:** уточняет FE-D17, FE-D27, FE-D29. Гейты идут по возрастанию стоимости, следующий — только после зелёного предыдущего: (1) в итерации разработки — `bash scripts/check-fast.sh` (`scripts/check-fast.js`: контракт задачи, ESLint по изменённым `.js`, Jest `--findRelatedTests`, тесты изменённых скриптов, Playwright по тегам кейсов контракта и изменённым спекам, при изменении общего файла `e2e/` — весь e2e; изменения от точки ответвления от `develop`); (2) `npm run accept` один раз; (3) `react-reviewer` тестов не запускает и судит по штампу приёмки (нет свежего штампа — BLOCKER без прогона); (4) `qa-tester` после APPROVE, а не параллельно с ревью, и проходит только объём `node scripts/check-state.js --qa-scope` — active-кейсы из «Кейсы» контракта плюс smoke `QA_SMOKE` = UC-SESSION-01, UC-CHAT-02, UC-MSG-01. `--require-qa` требует в отчёте строку `Объём:`, все кейсы контракта и smoke в ней и `pass` по каждому кейсу объёма. Задача — по имени ветки (`feature/FE-NN-…`); её кейсы — из контракта в «В работе», после закрытия — из обязательного поля «Кейсы:» записи в `done.md` (так проверка работает и в `git-task.sh commit`). Smoke-список не переопределяется окружением.
- **Почему:** токены и время уходили на повторные тяжёлые прогоны: полный `accept` в каждой итерации, тесты у ревьюера, браузерный проход всех active-кейсов при каждой задаче (провал FE-57 в `failures.md`) и его повтор после REJECT ревью. Пирамида верификации: дешёвая проверка первой, дорогая — только по уже зелёному.
- **Альтернативы:** QA до ревью (предложение пользователя) и QA параллельно с ревью — отвергнуты: замечание ревью меняет код и обнуляет самый дорогой гейт; полный проход всех active-кейсов — отвергнут: дублирует полный e2e из `accept`; smoke со входом UC-AUTH-01 — отвергнут: эпик passkey (FE-60) удаляет этот кейс; проверка памяти в `check-fast.sh` — отвергнута: в цикле код всегда свежее `tasks.md`, память проверяют hook `Stop` и `accept`.
- **Ревью (APPROVE WITH FIXES):** первая версия читала кейсы только из «В работе» (при коммите проверялся лишь smoke) и позволяла сузить smoke переменной `QA_SMOKE` — по выбору пользователя задача берётся из ветки, а кейсы закрытой задачи — из `done.md`.
- **Уточнено FE-D56 (2026-10-20):** smoke `QA_SMOKE` удалён; объём — кейсы контракта, полный проход — по триггерам.

## FE-D56 — Объём QA: кейсы контракта, полный проход по триггерам (2026-10-20)
- **Решение:** уточняет FE-D17, FE-D29, FE-D35. Smoke (`QA_SMOKE`) удалён. Обычная задача проходит в QA только active-кейсы из поля «Кейсы» контракта. Полный проход (все active-кейсы набора) обязателен, если дифф задачи (рабочее дерево + индекс + коммиты ветки от merge-base с `develop`, иначе `main`, + неотслеживаемые файлы) правит общую инфраструктуру — `src/app/store.js`, `src/app/reducers/auth.js`, `src/app/services/apiClient.js`, `authApi.js`, `wsService.js`, `mock-bff/**` — набор user-кейсов (`docs/user-cases.md`, `docs/user-cases/**`) или зависимости (`package.json`, `package-lock.json`), либо ветка `release/*` или `hotfix/*`. Закрытие эпика и слияние в `main` по диффу не определяются: объём запрашивается вручную флагом `--full` у `--qa-scope`. `--require-qa` пересчитывает триггеры сам и принимает любой отчёт, чей «Объём» содержит обязательный. Для полного прохода основная сессия запускает `qa-tester` с `model: opus`. Когда QA нужен вообще (FE-D29, `scripts/qa-required.sh`), не менялось. **Ограничение (выбор пользователя):** триггеры только расширяют объём там, где QA уже обязателен по `qa-required.sh` (правки `src/`, `mock-bff/`); обновление зависимостей, релиз и смена user-кейсов без правок `src/` и `mock-bff/` QA не запускают. Пустой объём (`--qa-scope` ничего не печатает): `qa-tester` стенд не поднимает и пишет отчёт с пустым «Объём:» и «Вердикт: PASS».
- **Почему:** выбор пользователя 2026-10-20 по анализу расхода токенов `qa-tester` (2026-10-17): smoke входил в объём 13 отчётов из 13, хотя его уже покрывает полный e2e в `npm run accept`; широкий проход нужен там, где правка может сломать кейсы вне контракта задачи.
- **Альтернативы:** оставить smoke в каждой задаче — отвергнуто (дублирует e2e, расход токенов); отдельный уровень «только smoke» — отвергнут: полный проход его включает; триггеры по списку кейсов или тегам вместо путей — не выбраны: пути проверяются механически.
