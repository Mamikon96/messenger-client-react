# Решения: Агент qa-tester

Формат записи и правила — `../decisions.md`. Записи до FE-D51 перенесены из исходного `decisions.md` без изменений.

## FE-D17 — Агент-тестировщик `qa-tester` поверх Playwright e2e (2026-10-09)
- **Решение:** `.claude/agents/qa-tester.md` — агент (только чтение кода + запись отчёта), сам поднимает приложение и проходит в браузере все `active`-кейсы из `docs/user-cases.md` (шаги и ожидаемое), основной проход — Playwright MCP, консоль и сеть — Chrome DevTools MCP. Результат — отчёт `.qa/report.md` (вне git): вердикт, матрица кейсов, проблемы с серьёзностью. Запускает основная сессия после зелёного `npm run accept`; проблемы исправляет `react-engineer`, затем повтор. Закрытие задачи: правило в `acceptance.md`/`CLAUDE.md` + проверка свежести и вердикта отчёта скриптом (`check-state.js --require-qa`, вызывается из `git-task.sh commit` для задач, меняющих `src/` или `mock-bff/`). Playwright e2e из приёмки **не убирается**: агент — второй, дополняющий гейт.
- **Почему:** выбор пользователя; детерминированный e2e ловит регрессии и держит покрытие кейсов, агент находит то, что тесты не проверяют (вёрстка, UX, расхождение описания кейса и экрана, консоль/сеть).
- **Альтернативы:** убрать e2e из приёмки (теряется воспроизводимость и привязка к тегам кейсов); только Playwright MCP или только DevTools MCP; гейт только правилом без проверки отчёта скриптом — не выбраны.
- **Ограничение (по ревью, 2026-10-09; путь сохранения заменён FE-D36, 2026-10-13):** ~~окружение может запретить субагенту писать файлы-отчёты; тогда `qa-tester` возвращает полный текст, а основная сессия сохраняет его в `.qa/report.md` дословно с пометкой под шапкой~~ — запасного пути больше нет: отчёт пишет сам `qa-tester` в `.qa/runs/<задача>.md`. Гейт опирается на содержимое отчёта (хэши и вердикт), поэтому он мягкий: отчёт может переписать любой, кто пишет файлы.

## FE-D36 — Отчёты qa-tester: файл на задачу в `.qa/runs/` (2026-10-13)
- **Решение:** уточняет FE-D17, FE-D35. Агент `qa-tester` сам пишет отчёт в `.qa/runs/<задача>.md`: `FE-NN.md` для ветки задачи, для ветки без ID — имя ветки с `/` → `-` (`chore-qa-runs.md`). Путь печатает `node scripts/check-state.js --qa-report-path`, его же читает `--require-qa`. Повторный проход по задаче перезаписывает её файл. `.qa/` уже в `.gitignore`, отдельная запись не нужна. Запасного пути «основная сессия сохраняет текст отчёта» нет (заменяет ограничение FE-D17): ошибка записи отчёта у `qa-tester` — стоп и вопрос пользователю (`ask-user.md`).
- **Почему:** Claude Code запрещает субагенту запись инструментом Write в файл с именем `report.md` («Subagents should return findings as text, not write report files»); проба 2026-10-13: `FE-00.md`, `.json` и запись через Bash проходят. Отчёт приходилось сохранять основной сессии, а единый `.qa/report.md` затирал историю проходов.
- **Альтернативы:** один перезаписываемый файл с другим именем (`.qa/qa-result.md`) — минимальная правка, но без истории; отдельная папка `qa-reports/` в корне — лишний каталог рядом с `.qa/`; запись отчёта через Bash heredoc — обход запрета харнесса, отвергнут. Выбор пользователя — файл на задачу.

## FE-D37 — Разрешения Playwright MCP и «Стенд: известное» для qa-tester (2026-10-13)
- **Решение:** уточняет FE-D17. В `.claude/settings.json` `permissions.allow` — инструменты Playwright MCP из списка `qa-tester`, кроме `browser_run_code_unsafe`; allow действует на все сессии и агентов проекта, не только на qa-tester (`browser_run_code_unsafe` выполняет произвольный код в Node с доступом к `page`, поэтому остаётся с запросом разрешения и в инструкции агента — только для `page.route` и того, что недоступно обычным инструментам). `browser_evaluate` разрешён: код выполняется только в странице. В `.claude/agents/qa-tester.md` — раздел «Стенд: известное»: вход — ссылки, ожидание после навигации, `browser_click` по ref, дефект FE-29 и его обход через `browser_evaluate` (а не `run_code_unsafe`, иначе запрос разрешения на пути UC-CHAT-02), короткие сценарии `run_code_unsafe`, остановка серверов `kill` по PID с порта (`pkill -f` убивает собственный шелл, exit 144 — воспроизведено), ожидание готовности циклом без длинного `sleep`.
- **Почему:** разбор транскриптов 5 проходов (FE-81, FE-57, FE-49, FE-46, chore user-cases-state-check): 22–54 вызова на проход, 4–6 ошибок в каждом; запрос разрешения на каждый вызов Playwright (в FE-57 отклонённый запрос оборвал прогон); таймауты кликов из-за оверлея FE-29, о котором агент не знал (обход есть только в e2e, которые ему читать запрещено); угадывание роли ссылки входа; гонки навигации в длинных скриптах; exit 144 от `pkill -f`.
- **Альтернативы:** allow вместе с `browser_run_code_unsafe` — отвергнут пользователем; разрешить агенту читать e2e-хелперы — отвергнуто: QA должен оставаться независимым гейтом (FE-D17), в раздел вынесены только факты о стенде; починить FE-29 — отдельная задача бэклога, не блокирует.

## FE-D43 — qa-tester: Playwright MCP для прохода, Chrome DevTools MCP для диагностики (2026-10-15)
- **Решение (выбор пользователя):** кейсы проходятся в Playwright MCP, после каждого кейса — его `browser_console_messages` и `browser_network_requests`; при `fail` или ошибке консоли/сети кейс повторяется в Chrome DevTools MCP, в отчёт идут стек ошибки (`get_console_message`) и тела запросов/ответов (`get_network_request`).
- **Почему:** Chrome DevTools MCP запускает отдельный браузер — прежняя инструкция «проходить в Playwright, консоль смотреть в Chrome DevTools» смотрела в другой браузер; повтор только проблемных кейсов даёт глубокую диагностику без двойного прохода.
- **Альтернативы (не выбраны):** Chrome DevTools как основной браузер (переписывать «Стенд: известное»); оба браузера на каждый кейс (~2× токенов QA).

## FE-D47 — qa-tester: дешёвый режим прохода (2026-10-17)
- **Решение:** уточняет FE-D17, FE-D43. Агент `qa-tester` по умолчанию на модели sonnet (было opus); основная сессия может запустить его с `model: opus` для рискованной задачи. Агенту запрещено открывать скриншоты через `Read`; скриншот только при `fail`. В инструкции бюджет ходов: ~8 на кейс, ~60 на проход, при превышении оставшиеся кейсы `blocked`, вердикт FAIL.
- **Почему:** замер 12 проходов: чтение кэша 0,4–21 млн токенов на проход (FE-40: 240 ходов, 21 млн; FE-39: 137 ходов, 8 млн), на Opus. Стоимость определяет число ходов, умноженное на растущий контекст, а не размер ответов Playwright; картинки из `Read` остаются в контексте до конца прохода.
- **Альтернативы (не выбраны здесь):** убрать smoke из обычного объёма и ввести полный проход по триггерам — вынесено в FE-116 (меняет скрипты и FE-D35); оставить Opus — дороже, качество находок не измерено.

## FE-D48 — QA: кейсы про отказы и тайминги не проходятся в браузере (2026-10-17)
- **Решение:** уточняет FE-D17, FE-D47. Кейсы про сбои сети, ретраи с backoff и лимиты `qa-tester` не проходит в браузере: в матрице отчёта они помечаются `pass (e2e)`. `check-state.js --require-qa` принимает такую отметку, только если у кейса есть e2e-тест с тегом `[UC-…]`.
- **Почему:** для таких кейсов агент каждый раз собирал мок через `page.route` и опрашивал его десятками вызовов, ожидая реальное время (FE-40: 240 ходов, 21 млн токенов чтения кэша), а детерминированно эти кейсы уже покрывает e2e из `npm run accept`.
- **Альтернативы (не выбраны):** управляемая имитация отказов в `mock-bff` для e2e и QA — дороже и добавляет код для поддержки.
