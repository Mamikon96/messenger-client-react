## SH-D02 — Приёмка задач через `npm run accept` (2026-10-04)
- **Решение:** задача завершена только при зелёных unit (Jest/RTL через react-scripts) и e2e (Playwright, chromium, dev-сервер на порту 3100). Единая точка входа — `scripts/accept.sh`.
- **Почему:** требование владельца проекта; один детерминированный критерий готовности.
- **Альтернативы:** Cypress (тяжелее), отдельные команды без общего скрипта (легко забыть e2e).
- **Примечание:** покрывает frontend (единственная сторона проекта, см. SH-D04).

## SH-D03 — Память разделена на frontend/backend + общий контракт (2026-10-04)
- **Решение:** отдельные `state/tasks/decisions/architecture` для каждой стороны в папках frontend/ и backend/ внутри памяти, общие файлы contracts.md и decisions.md; владение файлами по стороне; проверка структуры `scripts/check-memory.sh` в составе `npm run accept`.
- **Почему:** параллельная разработка frontend и backend без конфликтов правок памяти; отчёты агентов строятся из актуальных файлов своей стороны; механическая проверка защищает от устаревших/битых записей.
- **Альтернативы:** один общий набор файлов (конфликты при параллельной работе, смешение задач); монорепо-пакеты с отдельными CLAUDE.md (преждевременно, пока бэкенда нет).

## SH-D04 — Backend исключён из проекта, остаётся только frontend (2026-10-05)
- **Решение:** удалены `backend/` и `contracts.md` из памяти; в проекте одна сторона — frontend (папка `frontend/`, ID `FE-`). Решение SH-D03 в части backend/contracts утратило силу; в `check-memory.sh` убраны проверки backend. Формат с подпапкой `frontend/` сохранён, чтобы протокол `project-memory` работал без изменений.
- **Почему:** бэкенд в этом репозитории не нужен (владелец проекта); заглушки без содержимого вводили в заблуждение и требовали поддержки.
- **Альтернативы:** вернуть плоскую раскладку без `frontend/` (ломает единый протокол скилла, который ожидает подпапку стороны).

## SH-D05 — Решение фиксируется сразу после выбора пользователя; пишет solution-architect (2026-10-05)
- **Решение:** после ответа пользователя на `AskUserQuestion` решение с обоснованием («Решение / Почему / Альтернативы») записывается в `decisions.md`: если варианты готовил `solution-architect` — он сам (ему выдан `Edit` только для `decisions.md`, основная сессия передаёт ему выбор через `SendMessage`), иначе основная сессия. Уточняет FE-D03: согласием на запись считается сам выбор, запись не откладывается до конца реализации.
- **Почему:** агенты читают готовые решения и не изобретают их заново; причины фиксируются, пока свежи, а не после реализации; архитектор лучше всех знает, почему отклонены альтернативы.
- **Альтернативы:** запись основной сессией после реализации (прежний порядок — решения теряются или теряют контекст); отдельный вопрос «записывать ли?» (лишний шаг, выбор уже есть).

## SH-D06 — Жёсткое правило для всех агентов: сомнение или нехватка данных → вопрос пользователю (2026-10-05)
- **Решение:** любой агент при сомнении или нехватке данных спрашивает пользователя и ничего не придумывает (требования, поведение, значения, причины багов, факты о коде). Правило в `.ai/rules/ask-user.md`, п. 6 «Неснимаемых правил» `CLAUDE.md`, блок «Жёсткое правило» в каждом агенте `~/.claude/agents/*`. Агент без `AskUserQuestion` (ревьюеры, фоновые) возвращает вопросы вызывающему, основная сессия переадресует их пользователю.
- **Почему:** догадки агентов дают неверные требования и незаметные ошибки; цена вопроса ниже цены переделки.
- **Альтернативы:** правило только в `CLAUDE.md` (агенты вне проекта его не увидят); допущения «по умолчанию» с пометкой в отчёте (всё равно строит работу на выдумке).

## SH-D07 — PR создаётся автоматически после коммита задачи; ветка удаляется автоматически после слияния (2026-10-05)
- **Решение:** после `git-task.sh commit` агент сам пушит ветку и создаёт PR в `main` (пока нет `develop` в `origin`), без строки «Generated with Claude Code» в описании. Слияние и теги — по-прежнему только по просьбе. В репозитории включено «Automatically delete head branches»; `develop` и `release/*` защищены ruleset `protect-develop-release` (запрет удаления). Меняет прежнее «push и PR — только по просьбе» в `git-flow.md`.
- **Почему:** владелец проекта хочет, чтобы цикл задачи доходил до PR без лишних просьб, а ветки не копились. У GitHub нет галочки удаления при создании PR (есть только при слиянии), поэтому надёжнее настройка репозитория, чем флаг в каждой команде.
- **Альтернативы:** `gh pr merge --delete-branch` только при слиянии вручную (не работает при слиянии кнопкой в вебе); `gh pr merge --auto --delete-branch` при создании PR (требует auto-merge и противоречит правилу «слияние только по просьбе»).

## SH-D08 — Ветка `develop` опубликована в `origin`; PR задач идут в `develop` (2026-10-05)
- **Решение:** `develop` создана от `main` (e4827d4) и запушена в `origin` по просьбе пользователя. База PR для `feature/*`, `bugfix/*`, `chore/*` — `develop`; `release/*` и `hotfix/*` — `main`. Уточняет SH-D07 (там база `main`, «пока нет `develop`»).

- **Альтернативы:** оставить PR в `main` (противоречит git-flow, `main` должна быть только релизной).

## SH-D09 — Продукт: реальный мессенджер для малой закрытой группы, бэкенд — отдельный проект (2026-10-05)
- **Решение:** цель — реальный продукт (общение людей в реальном времени) для малой закрытой группы: до ~1 000 пользователей, один сервер, шифрование на транспорте (TLS), без E2EE. Бэкенд делается в **отдельном проекте/репозитории**; этот репозиторий остаётся frontend (SH-D04 не отменяется). Все соглашения по продукту, архитектуре и бэкенду — в `.ai/memory/product-agreements.md`; после создания проекта бэкенда работа продолжится там, а файл послужит входными данными.
- **Почему:** владелец проекта хочет настоящий мессенджер, а не демо; отдельный репозиторий не смешивает релизные циклы и процессы двух сторон.
- **Альтернативы:** клиент под внешний бэкенд на mock-BFF (не даёт реального продукта); учебный/портфолио-проект (не соответствует цели); публичный продукт с ростом, E2EE и корпоративный вариант (избыточны для малой группы, сильно усложняют архитектуру).

## SH-D10 — Основа бэкенда: Node.js + WebSocket + PostgreSQL (2026-10-05)
- **Решение:** собственный сервер на Node.js, реалтайм через WebSocket, данные в PostgreSQL. Продолжает контракт BFF/OAuth из `auth-contract.md`. Конкретные библиотеки (фреймворк, драйвер БД, WebSocket-слой) согласуются отдельно в проекте бэкенда по `tech-approval.md`.
- **Почему:** максимальный контроль и совместимость с уже зафиксированным контрактом auth; для ~1 000 пользователей объём бэкенда невелик; PostgreSQL даёт запас роста (индексы, полнотекстовый поиск, LISTEN/NOTIFY).
- **Альтернативы:** BaaS (Supabase/Firebase) — быстрый старт, но привязка к вендору и пересмотр контракта auth; Matrix (Synapse) — бэкенд не нужен, но тяжёлая модель протокола и контракт auth почти не нужен; «только клиент на mock-сервере» — не даёт реального продукта.

## FE-D03 — Процесс: память после любых изменений и согласование технологий (2026-10-05)
- **Решение:** (1) после любых изменений, до ответа пользователю, актуализируется `tasks.md` (и при необходимости `state.md`/`architecture.md`, штамп); (2) новая технология, библиотека или подход применяются только после опроса пользователя, а запись в decisions — только после его согласия; (3) `scripts/check-memory.sh` падает, если изменённые относительно HEAD файлы кода (`src/`, `e2e/`, `scripts/`, `package.json`, `playwright.config.js`) новее `tasks.md`.
- **Почему:** требование владельца проекта: память всегда актуальна, а выбор технологий остаётся за ним; проверка по времени изменения даёт механическую защиту от забытых обновлений.
- **Альтернативы:** обновлять память только по завершении задачи (риск устаревших данных между этапами); записывать решения автоматически (отвергнуто — решает владелец); проверка свежести через хук коммита (не выбрано: сложнее и срабатывает позже).

## FE-D04 — Авторизация: OAuth Google/GitHub через BFF с httpOnly-cookie сессией (2026-10-05)
- **Решение:** (1) вход только через OAuth Google/GitHub к своему API (бэкенд отдельный, пока не существует; контракт фиксируется заранее, на фронте мокается); email+пароль, passkeys, 2FA не делаем. (2) Архитектура BFF: кнопка провайдера делает полную навигацию на `/api/auth/{provider}/start`, код меняет сервер (state + PKCE), сессия хранится в cookie `HttpOnly; Secure; SameSite=Lax`, изменяющие запросы несут CSRF-заголовок. (3) Топология: SPA и API на одном сайте, только веб, других клиентов нет. (4) Фронт: слайс `auth` (`status` + `user`), единый apiClient с глобальной обработкой 401, сброс всего store при logout; в Redux и localStorage нет токенов и csrfToken; `loginService`/ключ `user` в localStorage уходят. (5) Без роутера: гейт по `auth.status` в `src/App.js`. (6) Мок M3 + M1: в Jest — подмена fetch/`authApi`, в Playwright — `page.route`, плюс локальный Node mock-BFF через CRA proxy для dev и e2e (затрагивает `playwright.config.js` и `scripts/accept.sh`).
- **Почему:** BFF — рекомендация RFC 10017 для приложений с персональными данными, и токены не попадают в JS; самый простой и тестируемый фронт, без новых пакетов; один сайт и отсутствие других клиентов снимают главный минус cookie-сессии; mock-BFF даёт настоящие редиректы, httpOnly-cookie и 401, близко к бою.
- **Альтернативы:** B — access в памяти + refresh-cookie с ротацией (отклонён: по RFC слабее BFF, сложный фронт — single-flight refresh, гонки между вкладками; нужен только для разных доменов или многих клиентов); C — только контракт + фейковый authApi (отклонён: не проверяет редиректы, cookie, 401 и CSRF, решение просто откладывается); MSW (отклонён: не эмулирует httpOnly-cookie и навигации, несовместим с Jest 27 в CRA без обходов, 3.0 слишком свежий); react-router-dom@7 (отклонён: сейчас не нужны URL и deep-links, достаточно гейта; v8 несовместим с React 18).

## FE-D05 — Авторизация: dev-прокси, контракт auth API, CSRF и истечение сессии (2026-10-05)
- **Решение:** уточняет FE-D04. (1) Dev-прокси — файл src/setupProxy.js (будет создан) на `http-proxy-middleware` 2.x, явно в devDependencies. (2) Контракт auth API ведётся Markdown-документом в `.ai/memory/` (не OpenAPI). CSRF-токен фронт получает из тела ответа `GET /api/auth/session`, хранит только в модуле apiClient (не в Redux и не в localStorage), отправляет в заголовке `X-CSRF-Token`. (3) Истечение сессии (401): сразу переход в `anonymous`, сброс store, экран входа с сообщением «сессия истекла»; черновик и открытый чат не сохраняются.
- **Почему:** поле `proxy` в package.json не проксирует навигацию (`Accept: text/html`), а `/api/auth/{provider}/start` — это полная навигация; явная зависимость не ломается при обновлении react-scripts. Markdown-контракт и токен в теле `/session` — выбор пользователя, без лишних инструментов. Простое поведение при 401 — выбор пользователя.
- **Альтернативы:** транзитивная копия `http-proxy-middleware` из react-scripts (хрупко); свой Node-прокси, объединяющий SPA и mock-BFF (сложнее); OpenAPI-файл для контракта; CSRF по схеме double-submit через читаемую cookie; модалка «войдите снова» с сохранением черновика.

## FE-D06 — Авторизация: поля user, срок сессии, сигнал ошибки OAuth (2026-10-05)
- **Решение:** уточняет FE-D04/FE-D05. (1) `user` в ответе `GET /api/auth/session` — `id`, `name`, `avatarUrl`, `provider`; email не передаётся. (2) Срок сессии — только абсолютный, 7 дней; idle-таймаута и «запомнить меня» нет. (3) Ошибка OAuth после callback — редирект на `/?auth_error=<код>` (`access_denied`, `provider_error`, `invalid_state`); фронт показывает сообщение и чистит URL через `history.replaceState`. Контракт целиком — `auth-contract.md`.
- **Почему:** минимальный набор данных профиля (меньше персональных данных); абсолютный срок проще для сервера; параметр в URL работает без роутера (FE-D04).
- **Альтернативы:** `user` с email (больше персональных данных, нужен только для связывания аккаунтов); idle 30 минут + абсолютный срок 7 дней; срок не фиксировать в контракте; ошибка OAuth через одноразовую временную cookie, отдаваемую `/api/auth/session` (сложнее).

## FE-D07 — UI: дизайн-токены на CSS custom properties и свой CSS, без UI-библиотек (2026-10-08)
- **Решение:** редизайн UI строится на дизайн-токенах (CSS custom properties: цвета, типографика, отступы, радиусы, тени, анимации). Темы переключаются атрибутом `data-theme` на `<html>`. Компоненты пишем сами, обычный CSS по БЭМ, по одному файлу на компонент. Новых зависимостей нет. Продолжает FE-D02 и `code-style.md`.
- **Почему:** выбор пользователя. Стек не меняется, зависимостей и бандла не прибавляется, тема меняется подменой переменных без перерендера.
- **Альтернативы:** CSS-токены + headless-библиотека (Radix UI) — меньше работы с a11y/фокусом у popover/меню, но новая зависимость (не выбрано); готовая UI-библиотека (MUI/Chakra) — тяжёлая и уходит от «обычного CSS» (не выбрано).

## FE-D08 — UI: три режима темы — светлая, тёмная, «как в системе» (2026-10-08)
- **Решение:** режимы `light` / `dark` / `system`. По умолчанию `system` (следует `prefers-color-scheme`), выбор пользователя хранится в localStorage (это настройка интерфейса, не данные сессии, FE-D04 не нарушается; сбрасывать при logout не нужно). Тема выставляется на `<html data-theme>` до первой отрисовки, без вспышки. Набор токенов рассчитан на добавление новых тем без правок компонентов. Развивает FE-D07.
- **Почему:** выбор пользователя; «как в системе» даёт верный первый визит, остальное — явное управление.
- **Альтернативы:** только светлая/тёмная без автоопределения; несколько акцентных цветовых схем × светлая/тёмная (больше токенов и тестов, не выбрано).

## FE-D09 — UI: визуальное направление «спокойный минимализм» (2026-10-08)
- **Решение:** стиль в духе Linear / Telegram Web: тонкие границы, один акцентный цвет, мягкие радиусы, аккуратная типографика, сдержанные анимации (с учётом `prefers-reduced-motion`). Контраст проверяется в обеих темах. Развивает FE-D07/FE-D08.
- **Почему:** выбор пользователя; одинаково хорошо смотрится в светлой и тёмной теме и проще поддерживать на токенах.
- **Альтернативы:** яркий и игривый (градиенты, цветные аватары — дороже по дизайну и контрасту); плотный деловой в духе Slack (не выбрано).

## FE-D10 — UI: объём редизайна (2026-10-08)
- **Решение:** кроме тем и визуала в задачу входят: адаптив под телефон (на узком экране одна панель за раз — список чатов или диалог, кнопка «назад»); состояния и микровзаимодействия (пустые состояния, скелетоны, автопрокрутка к последнему сообщению, аватары, плавные переходы); новый экран входа (список провайдеров из данных, загрузка, ошибки OAuth) и меню пользователя (аватар, переключатель темы). Отдельного пакета по клавиатуре/доступности нет, но базовые вещи (видимый фокус, Esc в меню/модалках, контраст AA в обеих темах) — часть каждого компонента. Развивает FE-D07…FE-D09.
- **Почему:** выбор пользователя.
- **Альтернативы:** отдельная задача на клавиатуру и a11y (не выбрана; базовый уровень остаётся в критериях компонентов).

## FE-D11 — Экран входа: тексты и поведение (2026-10-09)
- **Решение:** тексты ошибок OAuth (по `auth_error`, `auth-contract.md`) — короткие, без «Попробуйте ещё раз»: `access_denied` — «Вход отменён», `provider_error` — «Ошибка провайдера», `invalid_state` — «Попытка входа устарела», неизвестный код — «Не удалось войти». После клика по провайдеру кнопка показывает «Переход…» и индикатор, остальные кнопки неактивны (`aria-disabled`, клик игнорируется); при возврате из bfcache (`pageshow` с `persisted`) состояние сбрасывается. Провайдеры — данные (`id`, название, иконка), иконки Google и GitHub — простые инлайн-SVG без зависимостей. Ошибка читается из URL один раз в `App` и убирается из адреса через `history.replaceState` (FE-D06). `Button` получает `href` (рендерит ссылку). Уточняет FE-D06, развивает FE-D10.
- **Почему:** выбор пользователя по текстам; чтение ошибки в `App`, а не в `Login`, чтобы сообщение не терялось при перемонтировании `Login` после «Повторить».
- **Альтернативы:** развёрнутые тексты с «Попробуйте ещё раз» (не выбрано); чтение параметра в `Login` (теряется при перемонтировании).
